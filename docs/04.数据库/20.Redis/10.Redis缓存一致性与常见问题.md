## 先明确缓存允许旧多久

给查询加上 Redis，读请求变快了，但数据也多了一份副本。数据库提交成功时，缓存不一定已经同步完成。
设计之前先回答：这个接口允许读到几秒前的数据吗？缓存故障时，数据库能承担多少流量？

商品介绍、公开文章等场景通常可以接受短暂陈旧。库存扣减、付款金额确认等关键判断，应以有并发控制的权威数据源为准，不能依赖一个可能过期的缓存值。

本文以 MySQL 为事实来源、Redis 为可重建缓存，讨论常见的旁路缓存模式，也就是 Cache Aside。

## Cache Aside 的基本读写顺序

读数据：

1. 查询 Redis，命中则返回。
2. 未命中时查询 MySQL。
3. 把结果写入 Redis，设置过期时间，再返回。

写数据：

1. 在 MySQL 事务中修改业务数据。
2. 等待事务提交成功。
3. 删除对应缓存，让后续读取重新加载。

以下是流程伪代码，`afterCommit` 表示事务真正提交之后的回调，不是事务方法返回之前的普通函数调用：

```text
updateArticle(id, changes):
    transaction:
        update database article
        afterCommit:
            invalidate cache key article:{id}
```

这里选择删除，是因为“直接更新缓存”还需要处理两个写请求先后提交、却倒序写入缓存的情况。
如果先删缓存再提交数据库，读请求可能在中间读到旧值并回填。先提交数据库再删除缓存，可以避开这条常见竞态。

但上述三步并不是一个跨 MySQL 和 Redis 的原子事务，仍然需要处理失败和并发。

## 数据库成功了，删除缓存失败怎么办

可能的情况包括 Redis 超时、网络中断，以及应用在数据库提交后、执行删除前退出。
只记录一行日志会留下无人处理的旧缓存；仅在内存中重试，也无法覆盖进程退出。

一种可恢复的方案是事务 Outbox：

1. 修改业务数据时，在同一个 MySQL 事务中写入“缓存失效事件”。
2. 后台任务扫描已提交的事件，删除对应缓存。
3. 删除成功后标记完成，失败则按退避策略重试。
4. 重试耗尽的事件进入告警和人工补偿流程。

事件还可以通过消息队列投递，但“数据库提交后再发消息”本身也有失败窗口。Outbox 的意义在于，把业务修改与待发送事件一起提交。
消费成功后再确认消息；重复删除缓存通常是幂等的，因此可以接受至少一次投递。

CDC 订阅数据库变更也能驱动缓存失效，适合多个写入方无法统一改造的情况。两种方式都需要关注消费延迟和失败积压。

**可靠重试加 TTL 提供的是最终一致性策略。** 消息队列不会自动把数据库与缓存变成强一致的系统。
TTL 是兜底，不等于业务上可以不处理同步失败。

## 删除成功了，为什么还会读到旧数据

一个容易忽略的时序是：

| 顺序 | 读请求 A | 写请求 B |
| --- | --- | --- |
| 1 | 缓存未命中，开始查询旧数据 | |
| 2 | 查询结果尚未回填 | 更新数据库并提交 |
| 3 | | 删除缓存成功 |
| 4 | 把刚才读到的旧结果写入缓存 | |

最后缓存仍然是旧值。读请求如果访问存在复制延迟的只读库，风险窗口还可能扩大。

处理方式需要按业务选择：

- **接受短暂陈旧**：使用较短 TTL、可靠失效事件与监控，约定可接受的延迟。
- **协调读写**：同一个 Key 的重建与写入遵循统一互斥协议，在锁内重新检查缓存。只给读端加锁，并不能消除上表的写入竞态。
- **版本校验**：事件、数据和回填携带版本；由完整的原子比较协议拒绝旧版本。仅把版本号放进 JSON，并不会自动获得保护。
- **关键请求回源**：涉及业务决策时直接读取权威数据源，并由数据库事务或条件更新维护约束。

协调读写仍然受分布式锁租约、故障切换等条件影响。详细边界见 [Redis 分布式锁](/pages/redis-distributed-lock/)。

“延时双删”可以在第一次删除后，等一段时间再删除一次，降低慢查询回填旧值的概率。
但固定延迟很难覆盖任意长的查询、暂停和复制延迟；第二次删除也可能失败。
它可以作为补偿手段，不能写成“等 500 毫秒就一定一致”。

## 穿透、击穿、雪崩分别解决什么

| 问题 | 请求特征 | 主要处理方式 |
| --- | --- | --- |
| 穿透 | 查询的数据本来就不存在，每次都访问数据库 | 参数校验、短期缓存不存在结果、布隆过滤器、限流 |
| 击穿 | 某个热点 Key 失效，大量请求同时重建 | 合并并发回源、互斥重建、提前刷新、逻辑过期 |
| 雪崩 | 大量 Key 集中过期，或整个缓存服务不可用 | TTL 分散、分批预热、熔断降级、回源并发限制 |

### 穿透：不存在也可以缓存

对有效格式但不存在的 ID，可以缓存一个明确的空值标记，并使用较短 TTL。
要区分“缓存没有这个 Key”和“Key 存在但业务对象不存在”，否则仍会回源。

新建数据时也要删除对应空值缓存。不要把数据库超时或权限拒绝当作“对象不存在”缓存下来。

布隆过滤器能快速排除一部分不存在的数据，但有误判率。数据新增、删除和过滤器重建需要配套设计；同步不及时也可能误挡刚创建的数据。

### 击穿：让重建数量有上限

同一个进程内可以合并并发请求；多个实例间可以用互斥锁限制重建。
获得锁之后要再次读取缓存，因为等待期间其他请求可能已经完成回填。

未拿到锁的请求应有明确策略：短暂等待并限次重试、返回可接受的旧值，或者返回可解释的降级结果。
不要无限等待，也不要在每轮抢锁失败后都绕过锁查询数据库。

逻辑过期是一种不同的取舍：缓存保存内容与逻辑到期时间，到期后由少量请求触发后台刷新，其余请求暂时读取旧内容。
它适合允许陈旧数据的查询，需要同时定义最大陈旧时间和持续刷新失败时的行为。

### 雪崩：随机 TTL 只解决其中一部分

给基础 TTL 添加一定范围的随机偏移，能分散一批数据集中到期的时间。
但 Redis 整体不可用时，所有请求仍可能同时回源，随机 TTL 无法解决这个问题。

因此还要给数据库设置回源并发预算，按接口重要程度限流、降级；必要时使用容量受控的本地缓存。
本地缓存又多了一层副本，必须有过期与失效策略，不能把故障期间保留的值无限使用。

## 上线后看什么指标

缓存命中率不能单独说明系统健康。还应一起观察：

- 回源 QPS、并发数与数据库响应时间。
- 热点 Key 的重建耗时、失败数和等待数。
- 失效事件最老积压时间、重试次数和死信数量。
- 业务写入到查询可见的延迟，以及关键数据抽样对账结果。

验证时可以在测试环境模拟删除超时、进程中断、热点 Key 到期，以及“旧查询延迟回填”的时序。
预期结果应包含恢复过程：是否自动重试、多久恢复、恢复期间是否突破数据库承载能力。
