## 分布式锁解决哪一层问题

Java 的 `synchronized` 只能协调同一个 JVM 内的线程。服务部署多个实例后，多个进程仍可能同时重建热点缓存或执行同一批任务。
Redis 锁可以帮助这些实例协调操作，但它是一份会过期的租约，不能假设拿到锁后就永远独占资源。

本文先讨论单个 Redis 主节点上的基本协议，再说明它在业务超时和故障切换下的边界。
示例用于解释机制；生产代码优先采用成熟客户端，并验证其版本、拓扑与配置。

## 加锁：唯一令牌与过期时间必须一起设置

以下是 Redis 命令示意，`<request-token>` 必须替换成每次加锁尝试新生成的随机唯一令牌：

```text
SET lock:article:123 <request-token> NX PX 10000
```

- `NX`：仅在 Key 不存在时设置。
- `PX 10000`：租约为 10 秒，客户端退出后锁也能过期。
- 唯一令牌：标识本次持有者，不能所有请求都使用固定值 `1`。

只有收到 `OK` 才能认为此次获得锁；条件不满足时不能进入临界区。
不要拆成 `SETNX` 和 `EXPIRE` 两条命令，否则进程可能在中间退出，留下没有过期时间的锁。

网络超时则表示结果未知：Redis 可能已经设置成功，只是响应没有送达。
保守做法是不执行受保护操作，通过带令牌校验的清理或等待租约过期恢复，不能把超时当作成功。

## 解锁：比较持有者和删除必须原子执行

下面这个写法存在问题：

```text
finally:
    DEL lock:article:123
```

假设 A 持锁后长时间暂停，租约已过期，B 随后获得同一个锁。
A 恢复后执行 `DEL`，就会把 B 的锁删除。

以下 Lua 脚本用于原子校验与删除。运行前提是通过 Redis `EVAL` 或客户端脚本接口传入一个 Key，以及本次加锁保存的令牌：

```lua
-- KEYS[1]：锁 Key；ARGV[1]：本次持锁令牌
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

执行形式为 `EVAL <脚本字符串> 1 lock:article:123 <request-token>`。
返回 `1` 表示删除成功；返回 `0` 表示 Key 不存在或已不是本次请求持有。

不能先在客户端 `GET` 判断，再单独 `DEL`。两条命令之间仍然可能发生过期和重新加锁。
单 Key Lua 脚本可以避免这个检查与修改之间的竞态。

## 租约过期：安全解锁不等于安全执行业务

唯一令牌解决的是误删别人的锁，没有解决以下问题：

1. A 获得 10 秒租约，开始执行任务。
2. A 暂停超过 10 秒，锁过期。
3. B 获得新租约，开始执行同一任务。
4. A 恢复，继续操作数据库或外部服务。

此时 A、B 都可能执行临界区代码。即使 A 最终不会误删 B 的锁，业务资源已经存在并发访问。

常见缓解措施包括合理设置租期、限制业务执行时间、续期，以及在确认失去租约后取消后续操作。
但检查锁后再写数据库仍然有时间窗口；不可中断的调用也不会因为锁过期自动停止。

要求更严格时，可以使用 fencing token：每次获得锁时取得单调递增的编号，受保护资源拒绝比已接受编号更旧的操作。
随机令牌不具备这种顺序语义。编号的分配必须可靠，并且下游资源必须参与校验；仅把编号记录到日志中没有保护作用。

## 续期必须确认仍然拥有锁

续期也要原子比较令牌，不能对一个可能已被其他请求持有的 Key 直接延长 TTL：

```lua
-- KEYS[1]：锁 Key；ARGV[1]：令牌；ARGV[2]：新的租期毫秒数
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('PEXPIRE', KEYS[1], ARGV[2])
end
return 0
```

客户端应在租约到期前留足余量续期，并关注响应耗时和失败。
返回 `0` 表示已失去锁；网络超时也不能证明续期成功，应按保守策略处理后续工作。

续期线程也可能因 GC、CPU 饥饿、网络中断而错过截止时间，所以“有续期”仍不等于“绝不会并发”。
还要避免任务已经失控或无限阻塞，续期却持续运行，使其他请求长期无法推进。

## Redisson 的看门狗与显式租期

Redisson 的普通 `RLock` 提供可重入锁和自动续期能力。常见调用的区别如下，具体行为仍应对照项目实际使用版本：

| 调用方式 | 租期行为 |
| --- | --- |
| `lock.lock()` | 未指定租期，使用看门狗机制维持锁 |
| `lock.tryLock(waitTime, unit)` | 限制等待时间；成功后使用看门狗机制 |
| `lock.tryLock(waitTime, leaseTime, unit)` | 显式指定租期，到期自动释放，通常不启用看门狗续期 |

看门狗默认超时为 30 秒，可通过 `lockWatchdogTimeout` 调整。它是在客户端存活并且续期任务正常运行的条件下延长锁的过期时间。
显式设置 `leaseTime` 时，应确认业务能够在租期内完成，不能再假设看门狗会兜底。

下面是 Java 使用示意，前提是已配置 Redisson 客户端，且获取与释放发生在同一线程：

```java
RLock lock = redisson.getLock("lock:article:123");
boolean acquired = lock.tryLock(2, TimeUnit.SECONDS);
if (!acquired) {
    throw new IllegalStateException("当前任务正在处理中");
}
try {
    rebuildArticleCache();
} finally {
    // 失去锁后的业务处理需要另外设计，这个判断只辅助安全释放。
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

示例方法需要声明或处理 `InterruptedException`；捕获后应保留中断语义。
持有者检查与释放之间也可能过期，生产代码还需处理解锁异常，避免掩盖原业务异常。
不要将这个同步示例直接搬到切换线程的异步链路中。

## Redis 高可用不自动等于锁安全

使用异步主从复制时，主节点确认加锁后，锁可能尚未复制到副本。
如果此时主节点故障、副本被提升，新主节点上可能没有该锁，另一个请求就能再次获得锁。

因此要区分 Redis 服务的可用性与业务互斥性的要求。
Sentinel、Cluster 或客户端重试，不能自动消除所有锁丢失和并发执行窗口；涉及多节点锁算法时也要评估其时间与故障假设。

## 库存不能只靠一把 Redis 锁

库存是否能扣减，最终应由数据库中的原子条件更新或其他可靠的并发控制保证。
以下 SQL 假设 MySQL InnoDB、`id` 为唯一键，数量参数为正数，并且应用检查受影响行数：

```sql
UPDATE inventory
SET available = available - :quantity
WHERE id = :item_id
  AND available >= :quantity;
```

受影响行数为 `1` 才表示扣减成功；为 `0` 时不能继续按成功处理。
`:quantity`、`:item_id` 是参数占位符，不是可直接粘贴执行的 MySQL 字面量。

订单写入与库存扣减若要求一起成功，应放入同一数据库事务。
重复请求还需要业务幂等键或唯一约束。Redis 锁可以减少重复竞争，但不应代替这些数据约束。

验证分布式锁时，要覆盖任务超过租期、进程暂停、续期失败、解锁时换持有者及主节点切换。
判断标准不仅是“能抢到锁”，还包括失去锁之后业务是否会重复执行，以及数据层能否拒绝不合法的结果。
