## 把 Elasticsearch 看作可重建的搜索视图

MySQL 保存业务事实，Elasticsearch 提供全文检索和聚合，两者承担不同职责。
同步系统要回答三个问题：变更如何可靠送达、重复或乱序如何处理、发生差异后如何恢复。

本文默认 MySQL 是唯一事实来源，ES 索引可以从 MySQL 重建。
数据库提交成功到搜索结果更新之间允许一定延迟，具体时限需要由业务约定并监控。

订单是否付款、库存是否足够等业务决策，应查询权威数据源。搜索结果可以帮助找到对象，但不应替代提交操作时的业务校验。

## 常见同步方案如何选择

| 方案 | 工作方式 | 主要风险与适用情况 |
| --- | --- | --- |
| 同步双写 | 请求内先写 MySQL，再写 ES | 两边无法一起提交，任一失败都会留下补偿问题；简单系统也需要重试与对账 |
| 异步消息 | 提交数据后发送 MQ，由消费者写 ES | 降低请求耦合，但提交后发消息仍有丢失窗口；需可靠事件来源 |
| 事务 Outbox | 同一事务写业务表和事件表，再异步投递 | 业务变更与事件一起落库；需要清理、投递、去重和积压监控 |
| 定时扫描 | 按变更游标分批读取并写 ES | 运维相对简单，延迟取决于周期；删除、游标边界和漏扫需要额外设计 |
| CDC | 订阅 MySQL binlog，转换后写 ES | 减少业务侵入；需要管理快照、位点、保留时间和表结构变更 |

异步 MQ 和 CDC 都不能直接称为强一致。可靠投递解决“变更最终能到达”的问题，搜索何时可见还受消费延迟与 ES refresh 影响。

已有消息基础设施，且需要发布明确的业务事件时，可以考虑 Outbox。
写入来源多、希望统一捕获数据库变更时，可以考虑 Debezium、Canal 等 CDC 工具。
低变更量、可接受分钟级延迟的系统，定时同步也可能足够，没有必要统一选最复杂的方案。

## 为什么数据库提交后发 MQ 还不够

以下伪代码看起来合理，但中间存在故障窗口：

```text
commit MySQL transaction
publish change event to MQ
```

应用在第一步成功后退出，事件就没有发送。
如果改成先发消息，数据库后续又回滚，消费者则可能处理不存在的变更。

Outbox 把业务修改和事件写入同一个数据库事务：

```text
transaction:
    update business row and increase its version
    insert outbox event(id, entity_id, version, operation, payload)
commit

dispatcher:
    read pending committed events
    publish event
    mark event delivered after broker acknowledgement
```

发送成功、标记完成之前退出，事件会重复发送。因此消费者仍需要幂等，不能假设一条消息只处理一次。
多实例投递还需要认领机制，失败重试与死信记录必须可追踪。

事件可以携带完整快照，也可以携带主键让消费者回查数据库。后者可能读取到更新版本，必须把回查结果的版本和内容一起使用，不能把新内容配上旧事件版本。

## 全量导入与增量同步怎样衔接

直接“先导全量，再开始监听”容易漏掉全量导入期间发生的更新和删除。
正确衔接需要一致性快照和与它对应的增量起点：

1. 由连接器建立一致性快照，并记录对应的 binlog 位点或 GTID 状态。
2. 全量读取快照期间，保留后续增量日志，必要时缓冲增量事件。
3. 全量导入后，从保存的起点接续增量，并按工具协议处理重叠事件。
4. 等待增量追平，完成抽样与数量对账，再切换查询入口。

快照与位点不能由应用随便分两次查询拼起来。以 Debezium 为例，初始快照流程会协调锁、快照事务与日志位点，具体权限和影响取决于所选快照方式。

还要保证 binlog 保留时间大于可能的导入时长和故障恢复时长。
位点已经被清理时，不能仅从当前最新位置继续并宣称同步完整，需要重新快照或采取可验证的补数方案。

重建索引时，可以先写新索引，持续追增量，验证通过后再切换别名。
旧索引保留多久、失败如何回切、回切期间增量如何追平，都应提前定义。

## 幂等只能防重复，还要处理乱序

使用 MySQL 主键作为 ES 文档 `_id`，可以避免重试时创建多份文档。
但旧事件晚到，仍可能覆盖新内容。例如版本 12 已经写入，版本 11 才到达。

一种策略是为每个实体维护单调递增版本，并使用 ES 外部版本控制。
以下为 Elasticsearch REST 请求示意，前提是已创建合适的索引映射，且业务版本与文档内容来自同一次已提交变更：

```http
PUT articles/_doc/123?version=12&version_type=external
{
  "title": "更新后的文章标题",
  "version": 12,
  "deleted": false
}
```

`external` 只接受比当前版本更大的版本号。同版本重试和旧版本写入会出现版本冲突，应区分这类预期冲突与真正的处理失败。
只有确认版本协议正确、同一实体同版本代表同一内容后，才能把相应冲突作为已处理或过期事件。

不要随意使用 `external_gte` 来消除冲突：它允许相同版本覆盖，如果同版本携带不同内容，就失去了防护意义。
普通秒级时间戳也未必能唯一表示版本；同一秒的多次修改、时钟回拨、删除后主键重用都会破坏简单假设。

按实体 ID 分区可以减少乱序，但消费并发、重试队列、全量补数仍可能改变顺序。即使有顺序队列，也需要完整定义重放规则。

## 删除同步最容易遗漏

物理删除后，定时扫描业务表已经看不到这条记录，需要删除日志、Outbox、CDC 删除事件或软删除字段。
CDC 的行删除事件与某些消息系统用于日志压缩的空值 tombstone 也不是同一个概念，转换时要明确处理。

ES 删除 API 会暂时保留删除版本信息，但这个保护不会永久存在，受 `index.gc_deletes` 等设置影响。
旧写入事件如果很晚才重放，仍可能使已删除文档重新出现。

可选择保留带版本的逻辑删除文档，并在搜索中过滤 `deleted=true`，或维护可靠的删除版本记录与重放水位。
只有确认更旧事件不可能再次进入同步链路，才能安全清理对应的删除标记。
不能简单地把物理删除返回成功当作永久防复活保证。

## 定时扫描要留意游标和提交顺序

按 `updated_at` 增量扫描时，只使用“上次最大时间戳”可能漏掉相同时间戳的其他记录。
通常需要 `(updated_at, id)` 组合游标、稳定排序和分页，并设置适当的回看窗口，配合幂等处理重叠数据。

但回看窗口也不是完整证明：长事务可能很晚才提交，而它的更新时间却早于扫描水位。
如果不能约束这种延迟，应采用可靠的变更日志或 CDC，并通过周期性对账覆盖残余风险。

扫描方案还要确保所有更新路径都会维护变更字段，以及硬删除另有记录。只扫描“现存且更新时间较新”的行，无法发现 ES 中多出的文档。

## 消费成功不代表立刻能搜索到

ES 写入成功与搜索可见是两个时刻。搜索通常需要等待 refresh，这属于近实时搜索的正常行为。
不要为每条同步消息调用强制 refresh，这会增加资源消耗，影响吞吐。

少量确实需要写后可搜索的请求，可以评估 `refresh=wait_for`；批量同步则优先批处理和合理的刷新配置。
这只等待相应 ES 写入的可见性，不能消除它之前的 MySQL、MQ 和消费延迟。

使用 Bulk API 时，要逐项检查结果：HTTP 请求成功，并不代表每一个文档都写入成功。
可重试的限流或暂时故障采用退避重试；映射错误等持续失败应进入隔离队列，避免阻塞全部数据。

## 用补偿和对账让系统能够恢复

同步链路至少应监控源位点与消费位点差距、最老未处理事件时间、失败重试量、死信量，以及端到端搜索可见延迟。
只看队列长度，可能忽略低流量下某一条事件长时间卡住。

对账按主键范围或业务分片检查数量、缺失记录、冗余记录及版本差异。
数量相同并不代表内容一致，还需要抽样内容校验或稳定字段摘要比较。

补数应走同一版本与幂等协议，不能用不带版本的全量覆盖把新数据回滚。
验证方案时应模拟消息重复、倒序、消费退出、删除后旧消息重放，以及 binlog 位点失效等情况。
目标是确认系统既能持续同步，也能在中断后恢复到可解释、可核对的状态。
