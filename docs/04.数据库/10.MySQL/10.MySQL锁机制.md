更新一条数据，为什么另一个事务插入数据也会等待？理解这个问题，不能只看 SQL 最后改了几行，还要看执行过程中扫描了什么索引，以及事务使用什么隔离级别。

本文讨论 MySQL 8.x 的 InnoDB。示例结果按官方机制推导，可以在两个独立连接中复现；具体执行计划和锁范围应以实际版本为准。

## 先分清锁的层次

MySQL 的锁并不只有“表锁”和“行锁”两个选项。

| 类型 | 主要作用 | 常见场景 |
| --- | --- | --- |
| 表级数据锁 | 协调整张表的数据访问 | 显式表锁、MyISAM 的表级锁 |
| InnoDB 意向锁 | 表示事务准备在表内持有行级共享锁或排他锁 | 行级加锁之前自动取得 IS / IX |
| InnoDB 记录与范围锁 | 协调索引记录的修改和范围内插入 | 更新、删除、锁定读 |
| 元数据锁（MDL） | 协调表结构与表的使用 | 防止查询期间表被并发删除或修改结构 |

意向锁属于表级锁，但持有 IX 不意味着整张表不能被其他事务更新。不同事务的 IX 可以兼容，是否冲突还需要看它们访问的记录和范围。

因此，看到“表级锁”不能直接推导出“锁住所有行”。同样，MyISAM 使用表级数据锁，也不意味着表锁天然不会引发任何等待或死锁问题。

## 普通查询和锁定读

在读已提交（RC）和可重复读（RR）下，普通 `SELECT` 通常是快照读，通过 MVCC 读取可见版本，不申请记录锁或间隙锁。它仍涉及元数据锁，不能笼统说“完全不加锁”。

```sql
-- 普通查询：读取可见快照
SELECT * FROM lock_demo WHERE id = 10;

-- 锁定读：读取并锁住当前记录
SELECT * FROM lock_demo WHERE id = 10 FOR UPDATE;
SELECT * FROM lock_demo WHERE id = 10 FOR SHARE;
```

`FOR UPDATE` 取得排他锁（X），`FOR SHARE` 取得共享锁（S）。多个共享记录锁可以共存；同一记录上的排他锁与其他事务的共享锁、排他锁冲突。

需要在“查询后继续处理”的期间保留锁时，应显式开启事务。下面的所有加锁示例都这样做，最后用 `COMMIT` 或 `ROLLBACK` 结束事务、释放锁。

## 三种常见行级锁实际锁在哪里

InnoDB 的行级锁基于索引记录实现。即使没有显式主键，InnoDB 也会选择或生成聚簇索引，不存在“没有索引就无法使用行锁”的前提。

假设主键中只有 `10、20、30` 三个值：

| 类型 | 锁定对象 | 用区间表示 |
| --- | --- | --- |
| 记录锁（Record Lock） | 某条索引记录 | `id = 20` |
| 间隙锁（Gap Lock） | 相邻索引记录之间的空隙，不包含端点记录 | `(10, 20)` |
| 临键锁（Next-Key Lock） | 一条索引记录，加上它前面的间隙 | `(10, 20]` |

还可能锁定最小记录之前或最大记录之后的间隙。实际范围按索引顺序划分，不能只把 SQL 中写出的数值区间当成最终锁区间。

间隙锁的作用是阻止其他事务向间隙插入记录。两个事务可以同时持有同一个间隙上的间隙锁；这与“两个排他记录锁不能共存”不同。两边随后都尝试插入，仍可能出现等待或死锁。

插入操作还会使用插入意向锁。不同位置的插入意向锁不必互相阻塞，但会受到覆盖该位置的间隙锁约束。

## 用两次查询看清唯一索引的边界

先在测试库、事务外建立数据：

```sql
CREATE TABLE lock_demo (
    id INT PRIMARY KEY,
    score INT NOT NULL,
    note VARCHAR(50) NOT NULL,
    KEY idx_score (score)
) ENGINE = InnoDB;

INSERT INTO lock_demo VALUES
    (10, 100, 'A'), (20, 200, 'B'), (30, 300, 'C');
```

以下案例分开运行。每轮开始前结束上一轮的两个事务，确保测试数据仍只有初始化的三行。

### 等值查询命中已有主键

连接 A：

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM lock_demo WHERE id = 20 FOR UPDATE;
-- 暂时不要结束事务
```

连接 B：

```sql
START TRANSACTION;
INSERT INTO lock_demo VALUES (15, 150, 'new');
ROLLBACK;
```

B 插入 `15` 不会因为 A 对 `20` 的记录锁而等待，因为完整唯一键等值查询找到了记录，可以只锁该记录，不锁前面的间隙。B 如果更新 `id = 20`，则需要等待 A 结束。

在 A 执行 `ROLLBACK` 后开始下一轮。

### 等值查询的主键不存在

连接 A：

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM lock_demo WHERE id = 15 FOR UPDATE;
-- 返回空结果，但事务仍持有相应间隙锁
```

连接 B：

```sql
START TRANSACTION;
INSERT INTO lock_demo VALUES (15, 150, 'new');
-- 等待 A 结束事务；若等待过久，也可能先遇到锁等待超时
```

A 在另一个连接执行 `ROLLBACK` 后，B 的插入可以继续；B 再执行 `ROLLBACK` 恢复测试数据。

这里没有 `id = 15` 的记录可锁，RR 会锁住它所在的 `(10, 20)` 间隙。不能把“唯一索引等值查询只加记录锁”扩展到不存在的记录。

如果使用联合唯一索引，查询条件必须足以唯一定位记录；只使用联合索引的一部分列，不满足这个条件。可空唯一键也要考虑 MySQL 允许多个 `NULL` 的语义，不能直接套用非空唯一值的结论。

## 范围查询、非唯一索引与隔离级别

RR 下，锁定读、更新和删除需要根据扫描范围加记录锁、间隙锁或临键锁。例如：

```sql
START TRANSACTION;
SELECT * FROM lock_demo WHERE score >= 150 AND score < 250 FOR UPDATE;
-- 处理业务后结束事务
ROLLBACK;
```

这不是只锁住结果中的 `score = 200`。为保护扫描范围，还可能锁定相邻间隙；使用二级索引取得排他锁时，通常也会锁住对应的聚簇索引记录。

精确边界受索引、条件形式、执行计划和版本影响。分析复杂 SQL 时，应先用 `EXPLAIN` 看访问路径，再检查实际锁，避免背诵一条固定区间规则。

RC 下，搜索和索引扫描通常不使用间隙锁，但外键检查和重复键检查仍有例外；不符合条件的记录锁也可能提前释放。因此，不能把 RR 的加锁结果原样套到 RC。

## 没命中索引，不是“行锁升级成表锁”

```sql
START TRANSACTION;
UPDATE lock_demo SET score = score + 1 WHERE note = 'B';
ROLLBACK;
```

`note` 没有索引，执行计划可能扫描整个聚簇索引。RR 下，这会使加锁范围远大于最终更新的那一行，还可能阻塞其他事务插入。

原因是扫描范围扩大，记录锁和范围锁覆盖了更多数据，不能解释成 InnoDB 把行锁自动升级为了表锁。RC 的锁释放策略又有所不同，也不应一概声称“没有索引就锁全表”。

索引在这里不仅影响查询速度，还影响事务之间可以并发操作的范围。

## 怎样定位等待和死锁

在拥有相应查询权限的 MySQL 8.x 连接中，可以查看：

```sql
SELECT ENGINE_TRANSACTION_ID, OBJECT_SCHEMA, OBJECT_NAME,
       INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_STATUS, LOCK_DATA
FROM performance_schema.data_locks
WHERE OBJECT_NAME = 'lock_demo';

SELECT * FROM performance_schema.data_lock_waits;
SHOW ENGINE INNODB STATUS;
```

不要只看到 `X` 就判断锁住了某一行，还要结合索引名、`REC_NOT_GAP`、`GAP` 等信息，以及 SQL 的执行计划。

处理业务时，优先缩短事务、统一多行更新顺序、为过滤条件建立合适索引。数据库检测到死锁并回滚受害事务后，应用通常需要有界重试整个业务事务，而不是只重放最后一条 SQL。

锁等待超时与死锁的回滚范围不一定相同，遇到异常应显式结束当前事务，并按业务幂等性决定是否重试。
