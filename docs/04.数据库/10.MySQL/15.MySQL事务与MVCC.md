同一条记录，另一个事务已经修改并提交，当前事务为什么仍能查到旧值？这不是查询缓存没有刷新，而是 InnoDB 根据隔离级别和读视图，选择了当前事务可以看到的记录版本。

本文以 MySQL 8.x 的 InnoDB 为范围，先说明事务承诺什么，再拆开 MVCC 的版本选择过程。SQL 示例按官方机制说明预期结果，未包含本地数据库实测记录。

## 事务的四个特性分别解决什么

| 特性 | 含义 | 实际需要注意的地方 |
| --- | --- | --- |
| 原子性（Atomicity） | 事务中的修改整体提交或回滚 | 应用遇到业务失败时仍需主动回滚 |
| 一致性（Consistency） | 事务执行前后满足定义好的约束和业务规则 | 数据库约束之外的规则，还需要应用正确实现 |
| 隔离性（Isolation） | 控制并发事务可以观察和影响彼此的程度 | 不同隔离级别提供不同保证 |
| 持久性（Durability） | 已提交修改在故障恢复后仍可保留 | 具体保证受日志刷盘配置、存储设备等影响 |

例如转账要求“扣款和入账同时成功”，但如果应用只写扣款 SQL 就提交，数据库不会自动补出入账操作。事务机制帮助实现业务一致性，不能替代业务规则。

InnoDB 使用 undo 支持回滚和历史版本重建，使用 redo 支持崩溃恢复。undo、redo 和用于复制等场景的 binlog 是不同机制，不能混为一谈。

## 隔离级别决定并发时允许看到什么

| 隔离级别 | 普通读取的主要行为 |
| --- | --- |
| 读未提交（READ UNCOMMITTED） | 可能读到其他事务尚未提交的修改 |
| 读已提交（READ COMMITTED，RC） | 每次一致性读建立新的快照 |
| 可重复读（REPEATABLE READ，RR） | 同一事务的一致性读通常复用首次建立的快照；InnoDB 默认级别 |
| 串行化（SERIALIZABLE） | 提供更强隔离；显式事务中的普通查询可能转换为共享锁定读 |

“串行化”描述可观察结果的隔离保证，不等于数据库只能一个事务接着一个事务执行。不冲突的操作仍有并发空间。

三种常见现象也应分开理解：

- 脏读：读到了其他事务尚未提交、之后可能回滚的数据。
- 不可重复读：重复读取同一条已有记录，因其他事务提交修改而得到不同值。
- 幻读：重复执行相同条件的范围查询，因其他事务提交插入或删除，符合条件的行集合发生变化。

SQL 标准对 RR 的最低要求不排除幻读，但 InnoDB 的 RR 还结合了快照和范围锁。判断某段代码是否受并发插入影响，需要继续区分快照读与当前读，不能只背隔离级别对照表。

## 快照读与当前读

RC、RR 中普通的独立 `SELECT` 通常是一致性非锁定读，也叫快照读。它通过 MVCC 读取符合视图的历史版本，不需要阻止别人修改同一行。

```sql
SELECT balance FROM mvcc_account WHERE id = 1;
```

`SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE` 是锁定读。`UPDATE`、`DELETE` 也需要基于当前记录执行并加锁；学习时常把这些行为称为“当前读”。遇到冲突事务时可能等待，不能把“当前”理解为直接读取别人的未提交数据。

```sql
SELECT balance FROM mvcc_account WHERE id = 1 FOR UPDATE;
UPDATE mvcc_account SET balance = balance - 100 WHERE id = 1;
```

普通查询看不到某条新记录，并不代表唯一键检查、更新和删除也看不到它。数据库不能因为一个旧快照里没有该主键，就允许插入一条实际已存在的主键。

## 历史版本从哪里来

InnoDB 聚簇索引记录包含事务和回滚相关的隐藏信息：

| 字段 | 大小 | 用途 |
| --- | --- | --- |
| `DB_TRX_ID` | 6 字节 | 最近插入或更新该记录的事务 ID；删除也会以带删除标记的修改处理 |
| `DB_ROLL_PTR` | 7 字节 | 指向 undo 记录，用于重建前一个版本 |
| `DB_ROW_ID` | 6 字节 | InnoDB 需要生成隐藏聚簇索引时使用的行 ID |

表有合适主键或非空唯一索引时，会优先用它组织聚簇索引。因此，不应说所有表的每条索引记录都固定包含这三个隐藏字段。

更新产生 undo 信息后，可以沿回滚指针重建旧版本。假设余额经历了下面的修改，括号里是创建版本的事务 ID：

```text
balance = 800（120）→ balance = 900（110）→ balance = 1000（90）
         最新版本                 历史版本                 更早版本
```

这是一条用于理解可见性的逻辑版本链，不表示 undo 为每次修改都保存一份完整行副本。如果最新版本不可见，InnoDB 会继续重建并检查更早版本；没有可见版本时，这条记录对当前查询就不存在。

当旧版本不再被活动读视图等机制需要，purge 才能清理相应历史信息。长事务会拖延清理，这也是线上避免事务长时间不结束的原因之一。

## Read View 如何判断版本可见

Read View 记录建立快照时的事务状态，不是复制整张表。下面使用 MySQL 源码中的字段名，注意两个 limit 的英文名字容易与数值大小混淆。

| 字段 | 含义 |
| --- | --- |
| `m_creator_trx_id` | 创建视图的事务 ID，用于识别自己的修改 |
| `m_ids` | 建立视图时其他活跃读写事务的 ID 集合，不含创建者 |
| `m_up_limit_id` | `m_ids` 中最小 ID；集合为空时等于 `m_low_limit_id` |
| `m_low_limit_id` | 建立视图时的高水位；达到或超过它的版本来自之后分配 ID 的事务 |

只读事务可能尚未分配普通读写事务 ID，内部也会维护创建者信息；理解算法时应关注“自身修改可见”，不要假定每个 `BEGIN` 都立刻拿到一个递增写事务 ID。

比较对象是**当前待检查记录版本的 `DB_TRX_ID`**，不是“执行查询的事务 ID”。简化算法如下：

```text
version_trx_id = 当前版本的 DB_TRX_ID

如果 version_trx_id == m_creator_trx_id：可见（自己的修改）
否则如果 version_trx_id < m_up_limit_id：可见
否则如果 version_trx_id >= m_low_limit_id：不可见
否则：
    version_trx_id 在 m_ids 中：不可见
    version_trx_id 不在 m_ids 中：可见
```

`<` 和 `>=` 的边界不能漏掉。处于中间区间的事务，可能已经提交，也可能当时仍活跃，必须查询集合。

例如视图的创建者为 `115`，`m_ids = {110, 120}`，下界为 `110`，高水位为 `121`：

| 版本事务 ID | 是否可见 | 原因 |
| --- | --- | --- |
| 90 | 是 | 小于 110，建立视图前已提交 |
| 110 | 否 | 等于下界且位于活动集合 |
| 112 | 是 | 位于中间区间，但不在活动集合 |
| 115 | 是 | 当前事务自己的修改 |
| 120 | 否 | 建立视图时仍活跃 |
| 121 | 否 | 等于高水位，属于之后分配的事务 ID |

对前面的 `120 → 110 → 90` 版本链，这个视图最终选择 `90` 对应的余额 `1000`。即使事务 `110` 后来提交，只要仍使用这个视图，它的版本也不会突然变成可见。

## RC 和 RR 的区别在于何时建立视图

在测试库、事务外准备一张表：

```sql
CREATE TABLE mvcc_account (
    id INT PRIMARY KEY,
    balance INT NOT NULL
) ENGINE = InnoDB;
INSERT INTO mvcc_account VALUES (1, 1000);
```

下面按步骤在两个独立连接操作。

第一步，A 开启 RR 事务并查询，建立快照：

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT balance FROM mvcc_account WHERE id = 1; -- 1000
```

第二步，B 更新并提交：

```sql
START TRANSACTION;
UPDATE mvcc_account SET balance = 900 WHERE id = 1;
COMMIT;
```

第三步，A 再次查询，随后结束事务：

```sql
SELECT balance FROM mvcc_account WHERE id = 1; -- 仍为 1000
COMMIT;
SELECT balance FROM mvcc_account WHERE id = 1; -- 新事务读取 900
```

要对比 RC，先在没有未结束事务时把余额恢复为 `1000`，将 A 的隔离级别换为 `READ COMMITTED`，再按相同步骤执行。A 的第二次查询建立新视图，因此能够看到 B 已提交的 `900`。

RR 的视图通常由**第一次一致性读**建立，并非一执行 `START TRANSACTION` 就固定。如果 B 在 A 的第一次普通查询前已经提交，A 就能读到 B 的修改。

需要在开始时立即建立一致性快照，可以在 RR 下使用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`；该选项不会把其他隔离级别自动切换为 RR。

## 为什么混用两种读取会让人困惑

延续 RR 示例，在 B 提交之后、A 提交之前执行：

```sql
-- 仍读取原快照
SELECT balance FROM mvcc_account WHERE id = 1; -- 1000

-- 锁定读读取当前记录
SELECT balance FROM mvcc_account WHERE id = 1 FOR UPDATE; -- 900

-- UPDATE 基于当前值扣减
UPDATE mvcc_account SET balance = balance - 100 WHERE id = 1;

-- 自己的修改可见
SELECT balance FROM mvcc_account WHERE id = 1; -- 800
ROLLBACK;
```

锁定读不会把之前的普通查询快照整体刷新。自己修改后的版本可见，也不表示其他所有行都切换到了同一个最新时间点。因此，RR 中混用快照读和写操作，可能观察到“旧快照 + 自身修改”的组合。

涉及余额、库存等约束时，尽量把条件放进原子更新，例如 `UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0`，并检查受影响行数。确实需要先读再决策时，在同一事务内使用恰当的锁定读，而不是把普通查询得到的旧值直接写回。

关于范围内新记录的处理，还可以结合 [MySQL 锁机制](/pages/mysql-locks/) 阅读：快照读通过版本可见性得到稳定视图，RR 的锁定范围读取则通过范围锁限制其他事务插入，两者解决问题的方式不同。
