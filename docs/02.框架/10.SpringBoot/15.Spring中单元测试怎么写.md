# Java/Spring 项目单元测试入门：从 Service 层写起

从一个 Service 方法到底该怎么被测试开始。
你会看到 JUnit 5、Mockito、Spring Test、MyBatis-Plus 在测试里各自负责哪一块，以及项目里常见的这些写法为什么会出现：

```java
@ExtendWith(MockitoExtension.class)
@MockitoSettings(strictness = Strictness.LENIENT)
@Mock
@InjectMocks
@Spy
@BeforeEach
@AfterEach
@Nested
@DisplayName
@Test
assertEquals(...)
assertThrows(...)
when(...).thenReturn(...)
doReturn(...).when(...)
verify(...)
ReflectionTestUtils.setField(...)
TableInfoHelper.initTableInfo(...)
```

## 1. 先建立一个简单心智模型

一个 Service 层方法通常长这样：

```java
public Long register(RegisterCommand command) {
    // 1. 校验参数
    // 2. 查数据库判断是否重复
    // 3. 调用其他 service 或远程接口
    // 4. 写数据库
    // 5. 返回结果或抛异常
}
```

单元测试要做的事情不是把整个系统跑起来，而是单独验证这个方法在某些输入和依赖返回值下，是否做出了正确行为。

比如我们关心：

- 手机号为空时，是否抛出业务异常？
- 手机号已注册时，是否不会执行 insert？
- 邀请码不存在时，是否不会发送短信？
- 注册成功时，是否插入用户并调用远程短信接口？

测试的基本套路可以简化成四步：

```text
准备数据和依赖返回值
调用被测方法
断言返回值或异常
验证依赖有没有被正确调用
```

前三步也常被叫作 AAA：

```text
Arrange：准备数据和 mock 返回值
Act：调用被测方法
Assert：断言结果
```

`verify` 可以理解成 Assert 的一部分，只不过它断言的是“有没有发生某个调用”。

这四步后面会反复出现。

## 2. JUnit 5 是什么

JUnit 5 是 Java 里最常见的测试框架之一。它负责告诉测试运行器：

- 哪个类是测试类；
- 哪个方法是测试方法；
- 测试前后要做什么准备和清理；
- 断言失败时，如何把这个测试标记为失败。

在 Spring Boot 项目里，如果你引入了 `spring-boot-starter-test`，通常已经间接有了 JUnit 5、Mockito、Spring Test 等测试能力。

Maven 项目里常见依赖类似这样：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>
```

如果项目没有通过 Spring Boot starter 管理测试依赖，也可以单独引入 `junit-jupiter`、`mockito-core`、`mockito-junit-jupiter`、`spring-test`。微服务项目里一般优先跟随公司父工程或 Spring Boot BOM 的版本，不要随手混用多个不兼容版本。

### 2.1 测试类是什么

测试类就是专门用来验证某个类行为的类。通常放在：

```text
src/test/java
```

命名习惯一般是：

```text
被测类名 + Test
```

例如业务类叫 `UserServiceImpl`，测试类可以叫：

```java
class UserServiceImplTest {
}
```

测试类不是线上代码，不会被打进正常业务流程。它的职责是帮你确认业务类没有写错。

### 2.2 测试方法是什么

测试方法就是一个带 `@Test` 的方法。JUnit 看到 `@Test`，就知道这个方法需要被执行。

```java
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;

class UserServiceImplTest {

    @Test
    void shouldReturnNormalStatusWhenCreateUser() {
        UserServiceImpl userService = new UserServiceImpl();

        String status = userService.defaultUserStatus();

        assertEquals("NORMAL", status);
    }
}
```

这个方法里有三步：

```text
new 一个被测对象
调用业务方法
用 assertEquals 判断结果是不是预期值
```

### 2.3 断言是什么

断言就是“我认为结果应该是这样，如果不是，就让测试失败”。

最常见的是 `assertEquals`：

```java
assertEquals("NORMAL", status);
```

意思是：

```text
我期望 status 等于 NORMAL。
如果实际不是 NORMAL，这个测试失败。
```

再看一个更像 Service 层的例子：

```java
@Test
void shouldReturnUserNameWhenUserExists() {
    UserEntity user = new UserEntity();
    user.setId(1L);
    user.setName("张三");

    UserServiceImpl userService = new UserServiceImpl();

    String name = userService.getDisplayName(user);

    assertEquals("张三", name);
}
```

断言不是为了证明代码“跑过了”，而是为了证明结果“对了”。

### 2.4 @DisplayName 和 @Nested

`@DisplayName` 用来给测试类或测试方法起一个更适合人读的名字。

```java
@DisplayName("用户注册服务")
class UserServiceImplTest {

    @Test
    @DisplayName("用户昵称为空时返回默认昵称")
    void shouldReturnDefaultNameWhenNicknameIsBlank() {
        // test body
    }
}
```

`@Nested` 用来把同一个方法或同一类场景的测试分组。

```java
@DisplayName("用户服务测试")
class UserServiceImplTest {

    @Nested
    @DisplayName("register 方法")
    class RegisterTests {

        @Test
        @DisplayName("手机号为空时抛出异常")
        void shouldThrowWhenPhoneIsBlank() {
            // test body
        }

        @Test
        @DisplayName("手机号已存在时抛出异常")
        void shouldThrowWhenPhoneAlreadyExists() {
            // test body
        }
    }
}
```

对于新手，`@Nested` 的价值很直接：测试多了以后不会乱。你能一眼看出这组测试都在测 `register`。

如果外层测试类里有 `@BeforeEach` 和 `@AfterEach`，内层 `@Nested` 里的每个 `@Test` 也会照常执行这些准备和清理逻辑。后面的完整例子就依赖了这一点：外层统一设置租户上下文，内层每个注册场景都能拿到它。

### 2.5 @BeforeEach 和 @AfterEach

`@BeforeEach` 表示每个测试方法执行前都先执行它。

`@AfterEach` 表示每个测试方法执行后都执行它。

比如微服务里经常有租户上下文、用户上下文、MDC 日志上下文。这些东西通常存在 `ThreadLocal` 里，测试前设置，测试后清理。

```java
class TenantContextTest {

    @BeforeEach
    void setUp() {
        TenantContext.setTenantId(100L);
    }

    @AfterEach
    void tearDown() {
        TenantContext.clear();
    }

    @Test
    void shouldReadTenantIdFromContext() {
        assertEquals(100L, TenantContext.getTenantId());
    }
}
```

注意：不要把每个测试都不一定用到的 mock 返回值全部塞进 `@BeforeEach`。这样容易出现“这个测试到底依赖了什么”的阅读困难，也容易触发 Mockito 的 unused stubbing 问题。

## 3. Mockito 是什么，为什么要 mock

Mockito 是 Java 里常用的 mock 框架。它的核心作用是：在测试某个类时，把这个类依赖的对象替换成假的。

比如 `UserServiceImpl` 依赖：

```java
private final UserMapper userMapper;
private final MessageClient messageClient;
```

如果测试 `UserServiceImpl.register()` 时真的连数据库、真的调短信服务，这就不再是单元测试了。它会变慢、变脆弱，还可能因为外部环境不稳定导致测试失败。

所以单元测试里通常会：

- mock mapper，避免访问真实数据库；
- mock 其他 service，避免把测试扩散到另一个业务类；
- mock Feign Client、Dubbo Client、HTTP Client，避免真实远程调用；
- mock Redis、MQ、对象存储等基础设施客户端，避免依赖外部环境。

### 3.1 一个最小 Mockito 例子

假设业务方法是：

```java
class UserServiceImpl {
    private final UserMapper userMapper;

    UserServiceImpl(UserMapper userMapper) {
        this.userMapper = userMapper;
    }

    String getUserName(Long userId) {
        UserEntity user = userMapper.selectById(userId);
        if (user == null) {
            return "未知用户";
        }
        return user.getName();
    }
}
```

测试时不需要真实数据库：

```java
@ExtendWith(MockitoExtension.class)
class UserServiceImplTest {

    @Mock
    private UserMapper userMapper;

    @InjectMocks
    private UserServiceImpl userService;

    @Test
    void shouldReturnUserNameWhenUserExists() {
        UserEntity user = new UserEntity();
        user.setId(1L);
        user.setName("张三");

        when(userMapper.selectById(1L)).thenReturn(user);

        String name = userService.getUserName(1L);

        assertEquals("张三", name);
    }
}
```

这句是关键：

```java
when(userMapper.selectById(1L)).thenReturn(user);
```

它的意思是：

```text
当 userMapper.selectById(1L) 被调用时，不要查数据库，直接返回我准备好的 user。
```

### 3.2 @ExtendWith(MockitoExtension.class)

JUnit 5 本身只认识 `@Test`、`@BeforeEach` 这些测试注解。它并不知道 `@Mock` 应该怎么创建对象。

所以我们加：

```java
@ExtendWith(MockitoExtension.class)
```

这相当于告诉 JUnit 5：

```text
这个测试类里要启用 Mockito。
请帮我初始化 @Mock、@InjectMocks、@Spy 等对象。
```

完整写法：

```java
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)
class UserServiceImplTest {
}
```

如果没有这行，`@Mock` 字段很可能是 `null`，调用时就会空指针。

### 3.3 @MockitoSettings(strictness = Strictness.LENIENT)

有些项目里会看到：

```java
@MockitoSettings(strictness = Strictness.LENIENT)
```

完整写法：

```java
@ExtendWith(MockitoExtension.class)
@MockitoSettings(strictness = Strictness.LENIENT)
class UserServiceImplTest {
}
```

Mockito 默认会帮你检查一些“可疑测试写法”，例如你 stub 了某个返回值，但测试里根本没用到。这个检查通常是好事，因为它能发现无效准备代码。

`Strictness.LENIENT` 会放宽这些检查。它常见于老项目、复杂 `@Nested` 测试、或者 `@BeforeEach` 里有一些并非每个测试都用到的公共 stub。

新手建议：

- 新写测试时，不要一上来就加 `LENIENT`；
- 优先把 `when(...).thenReturn(...)` 写在真正需要它的测试方法里；
- 如果历史项目已经统一加了 `LENIENT`，你可以先遵循项目风格，但要知道它不是“更高级”，只是“更宽松”。

也可以只对单个 stub 放宽：

```java
lenient().when(configService.getRegisterSwitch()).thenReturn(true);
```

这样比整个测试类都 `LENIENT` 更克制。

## 4. @Mock、@InjectMocks、@Spy 的区别和使用场景

这三个注解非常容易混。先记一句话：

```text
@Mock 是假的依赖。
@InjectMocks 是真实的被测对象。
@Spy 是半真半假的对象。
```

### 4.1 @Mock：创建一个假对象

`@Mock` 创建的是 Mockito 生成的假对象。它不会执行真实逻辑。

```java
@Mock
private UserMapper userMapper;
```

默认情况下，mock 对象的方法会返回默认值：

- 对象返回 `null`；
- `int` 返回 `0`；
- `boolean` 返回 `false`；
- 集合可能返回空或 null，具体看返回类型和 mock 设置；
- void 方法什么都不做。

所以你通常要告诉它返回什么：

```java
when(userMapper.selectById(1L)).thenReturn(user);
```

适合用 `@Mock` 的对象：

- Mapper；
- Repository；
- Feign Client；
- Redis Client；
- MQ Producer；
- 其他 Service 依赖；
- 第三方 SDK 封装类。

小例子：

```java
@ExtendWith(MockitoExtension.class)
class UserServiceImplTest {

    @Mock
    private UserMapper userMapper;

    @Test
    void mockExample() {
        UserEntity user = new UserEntity();
        user.setName("张三");

        when(userMapper.selectById(1L)).thenReturn(user);

        assertEquals("张三", userMapper.selectById(1L).getName());
    }
}
```

这里的 `userMapper` 不会访问数据库。

### 4.2 @InjectMocks：创建被测对象，并把 mock 注进去

`@InjectMocks` 通常用在你真正要测试的类上。

```java
@Mock
private UserMapper userMapper;

@Mock
private MessageClient messageClient;

@InjectMocks
private UserServiceImpl userService;
```

Mockito 会尝试创建 `UserServiceImpl`，并把同一个测试类里的 `@Mock` 注入进去。

如果业务类是构造器注入：

```java
class UserServiceImpl {
    private final UserMapper userMapper;
    private final MessageClient messageClient;

    UserServiceImpl(UserMapper userMapper, MessageClient messageClient) {
        this.userMapper = userMapper;
        this.messageClient = messageClient;
    }
}
```

测试里这样写：

```java
@ExtendWith(MockitoExtension.class)
class UserServiceImplTest {

    @Mock
    private UserMapper userMapper;

    @Mock
    private MessageClient messageClient;

    @InjectMocks
    private UserServiceImpl userService;
}
```

你不需要手动：

```java
new UserServiceImpl(userMapper, messageClient);
```

不过要注意：

- `@InjectMocks` 不是 Spring，不会读取 `@Value`；
- `@InjectMocks` 不是 Spring，不会帮你创建项目里的所有 Bean；
- 如果某个依赖没有对应的 `@Mock`，它可能就是 `null`；
- 如果构造器复杂、重载很多，最好确认 Mockito 实际注入的是不是你以为的那条路径。
- 如果有多个同类型依赖、父类字段、复杂构造器，最稳的方式是放弃 `@InjectMocks`，在 `@BeforeEach` 里手动 `new` 被测对象。

例如：

```java
@Mock
private UserMapper userMapper;

@Mock
private MessageClient messageClient;

private UserServiceImpl userService;

@BeforeEach
void setUp() {
    userService = new UserServiceImpl(userMapper, messageClient);
}
```

这比猜 Mockito 的注入结果更清楚。

### 4.3 @Spy：半真半假的对象

`@Spy` 创建的是“真实对象的包装”。它默认会调用真实方法，但你可以把其中某些方法 stub 掉。

比如订单服务里有个生成订单号的方法依赖当前时间：

```java
class OrderServiceImpl {

    String createOrder(Long userId) {
        String orderNo = generateOrderNo();
        return orderNo + ":" + userId;
    }

    String generateOrderNo() {
        return "ORD-" + System.currentTimeMillis();
    }
}
```

测试时你不希望订单号每次都变，可以用 `@Spy`：

```java
@ExtendWith(MockitoExtension.class)
class OrderServiceImplTest {

    @Spy
    private OrderServiceImpl orderService;

    @Test
    void shouldCreateOrderWithFixedOrderNo() {
        doReturn("ORD-001").when(orderService).generateOrderNo();

        String result = orderService.createOrder(10L);

        assertEquals("ORD-001:10", result);
    }
}
```

这里：

- `createOrder(...)` 调真实方法；
- `generateOrderNo()` 被我们改成固定返回 `ORD-001`。

适合用 `@Spy` 的场景：

- 被测对象大部分逻辑要真实执行，只想替换一小段不稳定逻辑；
- 某个内部方法依赖时间、随机数、当前机器环境；
- 遗留代码还没来得及重构，只能先局部 stub。

不建议滥用 `@Spy`。如果你经常要 spy 被测类的很多内部方法，通常说明这个类职责太多，应该考虑把时间、随机数、外部规则等拆成独立依赖，然后用 `@Mock` 替换依赖。

### 4.4 三者对比

| 注解 | 对象真假 | 常见位置 | 默认行为 | 典型用途 |
|---|---|---|---|---|
| `@Mock` | 假对象 | 依赖对象 | 不执行真实方法，返回默认值 | mock mapper、远程接口、其他 service |
| `@InjectMocks` | 真实对象 | 被测类 | 执行业务真实逻辑 | 测 ServiceImpl 本身 |
| `@Spy` | 半真半假 | 被测类或少量依赖 | 默认执行真实方法，可局部 stub | 固定时间、随机数、遗留内部方法 |

最常见的 Service 单元测试组合是：

```java
@ExtendWith(MockitoExtension.class)
class UserServiceImplTest {

    @Mock
    private UserMapper userMapper;

    @Mock
    private MessageClient messageClient;

    @InjectMocks
    private UserServiceImpl userService;
}
```

如果你刚开始写测试，先掌握这个组合就够用了。

## 5. when(...).thenReturn(...) 和 doReturn(...).when(...) 的区别

这两个都能设置 mock 返回值，但它们在 `@Spy` 场景下差别很大。

### 5.1 普通 mock 场景：when(...).thenReturn(...) 最常见

对于 `@Mock` 对象，通常这样写：

```java
when(userMapper.selectById(1L)).thenReturn(user);
```

意思是：

```text
当 userMapper.selectById(1L) 被调用时，返回 user。
```

这是最常见、最自然的写法。

完整例子：

```java
@Test
void shouldReturnUserName() {
    UserEntity user = new UserEntity();
    user.setName("张三");

    when(userMapper.selectById(1L)).thenReturn(user);

    String name = userService.getUserName(1L);

    assertEquals("张三", name);
}
```

### 5.2 Spy 场景：推荐 doReturn(...).when(...)

对 `@Spy` 对象，如果你写：

```java
when(orderService.generateOrderNo()).thenReturn("ORD-001");
```

这里有个坑：`when(...)` 里面的方法会被立即调用一次。

也就是说，Mockito 在设置 stub 的时候，会先执行：

```java
orderService.generateOrderNo()
```

如果这个真实方法会查库、调远程、读配置、依赖尚未初始化的字段，测试可能在“准备阶段”就报错。

所以 Spy 场景更推荐：

```java
doReturn("ORD-001").when(orderService).generateOrderNo();
```

`doReturn(...).when(...)` 在设置 stub 时不会先调用真实方法。

对比一下：

```java
@Spy
private OrderServiceImpl orderService;

@Test
void badSpyStubbing() {
    // 不推荐：这里会先调用一次真实的 generateOrderNo()
    when(orderService.generateOrderNo()).thenReturn("ORD-001");
}

@Test
void goodSpyStubbing() {
    // 推荐：设置 stub 时不调用真实方法
    doReturn("ORD-001").when(orderService).generateOrderNo();
}
```

记忆方式：

```text
@Mock 依赖：when(...).thenReturn(...) 通常够用。
@Spy 对象：优先 doReturn(...).when(...)。
```

### 5.3 void 方法怎么办

如果是 void 方法，常见的不是 `thenReturn`，而是：

```java
doNothing().when(messageClient).sendWelcomeSms("13800000000");
```

不过多数情况下，mock 的 void 方法默认什么都不做，所以你甚至不需要写 `doNothing()`。

你更常做的是用 `verify` 验证它有没有被调用：

```java
verify(messageClient).sendWelcomeSms("13800000000");
```

## 6. assertThrows 怎么测试业务异常

业务代码里经常会抛自定义异常：

```java
if (phone == null || phone.isBlank()) {
    throw new BizException("手机号不能为空");
}
```

测试这种逻辑不要用 try-catch 手写，JUnit 5 提供了 `assertThrows`。

```java
@Test
void shouldThrowWhenPhoneIsBlank() {
    BizException exception = assertThrows(
            BizException.class,
            () -> userService.register(new RegisterCommand(""))
    );

    assertEquals("手机号不能为空", exception.getMessage());
}
```

这里分两层：

```text
assertThrows(BizException.class, ...)
断言这个调用一定会抛 BizException。

assertEquals("手机号不能为空", exception.getMessage())
进一步断言异常消息是不是预期的业务文案。
```

如果 `userService.register(...)` 没有抛异常，测试失败。

如果抛的是别的异常，比如 `NullPointerException`，测试也失败。

### 6.1 业务异常测试常见写法

```java
@Test
void shouldThrowWhenUserAlreadyExists() {
    when(userMapper.selectCount(any())).thenReturn(1L);

    BizException exception = assertThrows(
            BizException.class,
            () -> userService.register(new RegisterCommand("13800000000"))
    );

    assertEquals("手机号已注册", exception.getMessage());
}
```

这个测试表达的是：

```text
假设数据库里已经有这个手机号。
当调用注册方法。
应该抛出“手机号已注册”。
```

### 6.2 不要只测“抛了异常”

只写到这里还不够：

```java
assertThrows(BizException.class, () -> userService.register(command));
```

因为它只证明“有异常”，没证明是哪一种业务原因。

更好的写法是：

```java
BizException exception = assertThrows(
        BizException.class,
        () -> userService.register(command)
);
assertEquals("手机号已注册", exception.getMessage());
```

如果你的项目里业务异常有错误码，也建议断言错误码：

```java
assertEquals("USER_ALREADY_EXISTS", exception.getCode());
```

## 7. verify 怎么验证方法是否被调用

`assertEquals` 是验证结果。

`verify` 是验证交互。

Service 层经常不只是返回一个值，还会调用 mapper、发消息、调远程接口。这个时候就需要 `verify`。

### 7.1 验证某个方法被调用

```java
@Test
void shouldSendSmsWhenRegisterSuccess() {
    when(userMapper.selectCount(any())).thenReturn(0L);
    when(userMapper.insert(any(UserEntity.class))).thenReturn(1);

    userService.register(new RegisterCommand("13800000000"));

    verify(messageClient).sendWelcomeSms("13800000000");
}
```

默认等价于：

```java
verify(messageClient, times(1)).sendWelcomeSms("13800000000");
```

意思是这个方法应该被调用 1 次。

### 7.2 验证某个方法没有被调用

手机号已经注册时，不应该插入新用户，也不应该发送短信：

```java
@Test
void shouldNotInsertOrSendSmsWhenPhoneAlreadyExists() {
    when(userMapper.selectCount(any())).thenReturn(1L);

    assertThrows(
            BizException.class,
            () -> userService.register(new RegisterCommand("13800000000"))
    );

    verify(userMapper, never()).insert(any(UserEntity.class));
    verify(messageClient, never()).sendWelcomeSms(anyString());
}
```

`never()` 很适合验证异常分支是否提前返回。

### 7.3 验证调用次数

```java
verify(userMapper, times(1)).selectCount(any());
verify(messageClient, never()).sendWelcomeSms(anyString());
```

常见次数写法：

```java
verify(userMapper, times(1)).insert(any(UserEntity.class));
verify(userMapper, never()).deleteById(anyLong());
verify(messageClient, atLeastOnce()).sendWelcomeSms(anyString());
```

新手建议少用 `atLeastOnce()`。它比较宽松，容易让测试失去精确性。业务测试里多数时候你知道应该调用 0 次还是 1 次。

### 7.4 verifyNoInteractions 和 verifyNoMoreInteractions

如果你想确认某个 mock 完全没有被碰过：

```java
verifyNoInteractions(messageClient);
```

如果你已经验证了一些调用，并想确认没有其他多余调用：

```java
verify(userMapper).selectCount(any());
verifyNoMoreInteractions(userMapper);
```

不要到处加 `verifyNoMoreInteractions`。它会让测试过度绑定实现细节。只有当“不能有额外调用”本身就是业务要求时，再加。

### 7.5 any、anyString、argThat 是什么

前面的例子里出现了这些写法：

```java
when(userMapper.selectCount(any())).thenReturn(0L);
verify(messageClient, never()).sendWelcomeSms(anyString());
verify(userMapper).insert(argThat(user -> "NORMAL".equals(user.getStatus())));
```

它们叫参数匹配器。意思是：我不关心参数必须等于某个固定对象，只关心它符合某种范围或条件。

常见匹配器：

```java
any()                    // 任意对象
any(UserEntity.class)    // 任意 UserEntity 对象
anyString()              // 任意字符串
anyLong()                // 任意 Long 或 long
argThat(...)             // 自己写条件判断
```

比如你只想让查重返回 0，不关心 `LambdaQueryWrapper` 对象内部长什么样：

```java
when(userMapper.selectCount(any())).thenReturn(0L);
```

如果你想验证插入的用户状态是 `NORMAL`，可以用 `argThat`：

```java
verify(userMapper).insert(argThat(user ->
        user != null && "NORMAL".equals(user.getStatus())
));
```

`argThat` 适合验证“传给 mapper 的实体内容对不对”。不过它也有缺点：条件复杂时，失败信息不一定直观。条件太多时，可以改用 `ArgumentCaptor` 捕获参数后再断言：

```java
ArgumentCaptor<UserEntity> captor = ArgumentCaptor.forClass(UserEntity.class);

verify(userMapper).insert(captor.capture());

UserEntity user = captor.getValue();
assertEquals("13800000000", user.getPhone());
assertEquals("NORMAL", user.getStatus());
```

新手还要记住一个规则：同一个方法调用里，如果一个参数用了 matcher，其他参数通常也要用 matcher。

不要这样混用：

```java
when(orderMapper.selectByUserIdAndStatus(anyLong(), "PAID")).thenReturn(order);
```

更稳妥：

```java
when(orderMapper.selectByUserIdAndStatus(anyLong(), eq("PAID"))).thenReturn(order);
```

其中 `eq("PAID")` 的意思是：这个参数必须等于 `"PAID"`。

## 8. ReflectionTestUtils.setField 为什么会出现在测试里

`ReflectionTestUtils` 是 Spring Test 提供的反射工具。它经常出现在单元测试里，是因为 Mockito 单元测试不会启动 Spring 容器。

看一个业务类：

```java
class UserServiceImpl {

    @Value("${user.default-status:NORMAL}")
    private String defaultStatus;

    String defaultUserStatus() {
        return defaultStatus;
    }
}
```

如果你用的是：

```java
@ExtendWith(MockitoExtension.class)
```

这个测试没有启动 Spring，所以 `@Value` 不会生效。`defaultStatus` 可能是 `null`。

这时可以用：

```java
ReflectionTestUtils.setField(userService, "defaultStatus", "NORMAL");
```

完整例子：

```java
@ExtendWith(MockitoExtension.class)
class UserServiceImplTest {

    @InjectMocks
    private UserServiceImpl userService;

    @BeforeEach
    void setUp() {
        ReflectionTestUtils.setField(userService, "defaultStatus", "NORMAL");
    }

    @Test
    void shouldReturnDefaultStatus() {
        assertEquals("NORMAL", userService.defaultUserStatus());
    }
}
```

### 8.1 它适合解决什么问题

`ReflectionTestUtils.setField` 常见用途：

- 给 `@Value` 注入的私有字段赋值；
- 给遗留代码里的 private 字段赋值；
- 替换不方便通过构造器传入的配置项；
- 测试没有 setter 的对象状态。

例如：

```java
@BeforeEach
void setUp() {
    ReflectionTestUtils.setField(orderService, "maxCreateCountPerDay", 5);
}
```

### 8.2 它不应该被滥用

如果一个依赖本来可以通过构造器传入，就不要用反射硬塞。

优先推荐业务代码写成构造器注入：

```java
class UserServiceImpl {
    private final UserMapper userMapper;

    UserServiceImpl(UserMapper userMapper) {
        this.userMapper = userMapper;
    }
}
```

测试里：

```java
@Mock
private UserMapper userMapper;

@InjectMocks
private UserServiceImpl userService;
```

这样比反射更清楚。

可以把 `ReflectionTestUtils.setField` 当成一个补位工具：对配置字段和遗留代码很有用，但不要让它成为主要注入方式。

### 8.3 什么时候用纯 Mockito，什么时候用 Spring Test

Spring 项目里的测试大致可以分三类。刚开始写 Service 单元测试时，先分清自己在哪一类里。

| 你要测什么 | 推荐方式 | 特点 |
|---|---|---|
| 只测一个 Service 的业务判断 | `@ExtendWith(MockitoExtension.class)` + `@Mock` | 快，不启动 Spring，适合大多数 Service 单元测试 |
| 要验证 Spring 配置、AOP、事务、Bean 装配 | Spring Test，例如 `@SpringBootTest` | 更接近真实环境，但更慢 |
| 启动 Spring 后替换容器里的某个 Bean | `@MockitoBean` / `@MockitoSpyBean`，老 Spring Boot 项目常见 `@MockBean` | 适合集成测试里替换远程接口或外部依赖 |

纯 Mockito 的测试里：

```java
@ExtendWith(MockitoExtension.class)
class UserServiceImplTest {

    @Mock
    private MessageClient messageClient;

    @InjectMocks
    private UserServiceImpl userService;
}
```

这个 `messageClient` 只存在于当前测试类里，不是 Spring 容器里的 Bean。

Spring Test 里替换 Bean 时，写法会变成：

```java
@SpringBootTest
class UserApiIntegrationTest {

    @MockitoBean
    private MessageClient messageClient;

    @Autowired
    private UserService userService;

    @Test
    void shouldRegisterUser() {
        // test body
    }
}
```

这里的 `@MockitoBean` 会把 Spring 容器里的 `MessageClient` 替换成 Mockito mock。老版本 Spring Boot 项目里，你更常看到的是 `@MockBean`，思路类似。

新手建议先写纯 Mockito 单元测试。只有当你明确要验证 Spring 容器行为时，再用 `@SpringBootTest` 这一类测试。

## 9. MyBatis-Plus 里 TableInfoHelper.initTableInfo 的作用

MyBatis-Plus 会维护实体类和数据库表之间的元信息，例如：

- 实体类对应哪张表；
- 主键字段是什么；
- Java 字段对应数据库列是什么；
- LambdaQueryWrapper 里的 `UserEntity::getPhone` 应该解析成哪个列名。

这些信息会缓存在 `TableInfoHelper` 里。

在正常 Spring Boot 启动时，MyBatis-Plus 通常会扫描 Mapper 和实体，完成这些初始化。但在纯 Mockito 单元测试里，我们没有启动 Spring，也没有启动 MyBatis。于是某些代码如果真实执行了 MyBatis-Plus 的 lambda wrapper 逻辑，就可能遇到元信息没有初始化的问题。

典型业务代码：

```java
Long count = userMapper.selectCount(
        Wrappers.<UserEntity>lambdaQuery()
                .eq(UserEntity::getPhone, phone)
);
```

虽然 `userMapper.selectCount(...)` 是 mock 的，不会真的查数据库，但 `Wrappers.lambdaQuery().eq(...)` 是业务代码里的真实逻辑，会在调用 mock 之前先执行。它需要知道 `UserEntity::getPhone` 对应哪个字段。

这时测试里可能需要手动初始化实体元信息：

```java
private void initMyBatisPlusTableInfo() {
    if (TableInfoHelper.getTableInfo(UserEntity.class) != null) {
        return;
    }

    MybatisConfiguration configuration = new MybatisConfiguration();
    MapperBuilderAssistant assistant = new MapperBuilderAssistant(configuration, "");

    TableInfoHelper.initTableInfo(assistant, UserEntity.class);
}
```

如果你的测试确实因为 MyBatis-Plus lambda 元信息失败，可以在测试准备阶段调用它：

```java
@BeforeEach
void setUp() {
    initMyBatisPlusTableInfo();
}
```

但这不是所有 MyBatis-Plus 单元测试的固定模板。它更像排障工具：只有当纯 Mockito 测试执行到 `LambdaQueryWrapper` 构造，并且你的项目版本、实体注解、缓存状态导致元信息找不到时，才需要加。

### 9.1 什么时候需要它

常见需要的情况：

- Service 方法里会真实构造 `LambdaQueryWrapper`；
- 测试没有启动 Spring 容器；
- 测试没有加载 MyBatis-Plus 的 Mapper 扫描；
- 报错类似 lambda column cache、TableInfo 找不到、实体元信息未初始化。

### 9.2 什么时候不需要它

这些情况通常不需要：

- 你用的是 `@SpringBootTest`，Spring 和 MyBatis-Plus 都启动了；
- 你用的是 MyBatis-Plus 提供的 `@MybatisPlusTest` 来测 Mapper 或 MyBatis-Plus 集成行为；
- 你只 mock 了 mapper，且业务代码没有执行 MyBatis-Plus wrapper 构造逻辑；
- 你的测试只验证简单参数校验，还没走到 wrapper 那一行。

不要把 `TableInfoHelper.initTableInfo(...)` 当成所有 MyBatis-Plus 测试的固定模板。它是为了解决“纯单元测试里缺少 MyBatis-Plus 元数据初始化”的问题。

### 9.3 @MybatisPlusTest 和 TableInfoHelper 怎么选

如果你要测的是 Mapper、SQL、自动填充、主键回填、分页插件、逻辑删除这类 MyBatis-Plus 集成行为，更适合用 MyBatis-Plus 的测试支持：

```java
@MybatisPlusTest
class UserMapperTest {

    @Autowired
    private UserMapper userMapper;

    @Test
    void shouldInsertUser() {
        UserEntity user = new UserEntity();
        user.setPhone("13800000000");

        userMapper.insert(user);

        assertNotNull(user.getId());
    }
}
```

如果你要测的是 Service 的业务分支，并且 mapper 已经被 `@Mock` 替换，那还是优先用纯 Mockito。只有纯 Mockito 执行真实 `LambdaQueryWrapper` 构造时遇到元信息问题，才考虑 `TableInfoHelper.initTableInfo(...)`。

### 9.4 ServiceImpl 和 baseMapper 场景

MyBatis-Plus 项目里还经常看到：

```java
class UserServiceImpl extends ServiceImpl<UserMapper, UserEntity> {

    Long countByPhone(String phone) {
        return lambdaQuery()
                .eq(UserEntity::getPhone, phone)
                .count();
    }
}
```

这种写法里，`baseMapper` 是 `ServiceImpl` 父类里的字段。纯 Mockito 测试时，如果你直接 `@InjectMocks`，有时不容易看清父类字段是否被正确注入。

遇到这种遗留或框架父类字段，可以用 `ReflectionTestUtils` 明确塞进去：

```java
@Mock
private UserMapper userMapper;

private UserServiceImpl userService;

@BeforeEach
void setUp() {
    userService = new UserServiceImpl();
    ReflectionTestUtils.setField(userService, "baseMapper", userMapper);
}
```

这类测试要更谨慎：如果你测的是 `lambdaQuery().count()` 本身和数据库行为，应该走 `@MybatisPlusTest`；如果只是让 Service 分支继续往下走，mock `baseMapper` 才合适。

## 10. 从头写一个完整 Service 层测试类

下面用一个简化版用户注册业务串起来。

业务规则：

- 必须有租户上下文；
- 手机号不能为空；
- 手机号不能重复；
- 如果传了邀请码，邀请码必须存在；
- 注册成功后插入用户；
- 插入成功后发送欢迎短信；
- 插入失败时抛业务异常，不发送短信。

这个例子故意贴近 Spring Boot / Spring Cloud 微服务里的 Service 层，而不是纯算法。

为了方便理解，下面会先展示生产代码，再展示测试代码。如果放到真实项目里，大概是这样的文件布局：

```text
src/main/java/com/example/user/UserServiceImpl.java
src/main/java/com/example/user/UserEntity.java
src/main/java/com/example/user/UserMapper.java
src/main/java/com/example/user/InviteCodeService.java
src/main/java/com/example/user/MessageClient.java
src/main/java/com/example/user/BizException.java
src/main/java/com/example/user/TenantContext.java

src/test/java/com/example/user/UserServiceImplTest.java
```

文章里为了减少跳转，把这些类集中展示。真实项目中不要把所有类都塞进一个文件。

### 10.1 被测业务代码

为了让示例完整，这里把相关类都放在一起展示。真实项目中它们会分散在 `entity`、`mapper`、`service`、`client`、`exception` 等包里。

```java
import com.baomidou.mybatisplus.annotation.TableId;
import com.baomidou.mybatisplus.annotation.TableName;
import com.baomidou.mybatisplus.core.mapper.BaseMapper;
import com.baomidou.mybatisplus.core.toolkit.Wrappers;

class UserServiceImpl {

    private final UserMapper userMapper;
    private final InviteCodeService inviteCodeService;
    private final MessageClient messageClient;

    // 假设真实项目里这个字段来自 @Value("${user.default-status:NORMAL}")
    private String defaultStatus;

    UserServiceImpl(UserMapper userMapper,
                    InviteCodeService inviteCodeService,
                    MessageClient messageClient) {
        this.userMapper = userMapper;
        this.inviteCodeService = inviteCodeService;
        this.messageClient = messageClient;
    }

    Long register(RegisterCommand command) {
        Long tenantId = TenantContext.getTenantId();
        if (tenantId == null) {
            throw new BizException("租户信息不能为空");
        }

        if (command == null || !hasText(command.getPhone())) {
            throw new BizException("手机号不能为空");
        }

        String phone = command.getPhone().trim();

        Long count = userMapper.selectCount(
                Wrappers.<UserEntity>lambdaQuery()
                        .eq(UserEntity::getTenantId, tenantId)
                        .eq(UserEntity::getPhone, phone)
        );
        if (count != null && count > 0) {
            throw new BizException("手机号已注册");
        }

        Long inviterId = null;
        if (hasText(command.getInviteCode())) {
            InviteCode inviteCode = inviteCodeService.findByCode(command.getInviteCode().trim());
            if (inviteCode == null) {
                throw new BizException("邀请码不存在");
            }
            inviterId = inviteCode.getOwnerUserId();
        }

        UserEntity user = new UserEntity();
        user.setTenantId(tenantId);
        user.setPhone(phone);
        user.setInviterId(inviterId);
        user.setStatus(defaultStatus);

        int inserted = userMapper.insert(user);
        if (inserted != 1) {
            throw new BizException("注册失败");
        }

        messageClient.sendWelcomeSms(phone);
        return user.getId();
    }

    private boolean hasText(String value) {
        return value != null && !value.trim().isEmpty();
    }
}

class RegisterCommand {
    private String phone;
    private String inviteCode;

    RegisterCommand(String phone) {
        this.phone = phone;
    }

    RegisterCommand(String phone, String inviteCode) {
        this.phone = phone;
        this.inviteCode = inviteCode;
    }

    String getPhone() {
        return phone;
    }

    String getInviteCode() {
        return inviteCode;
    }
}

@TableName("sys_user")
class UserEntity {
    @TableId
    private Long id;
    private Long tenantId;
    private String phone;
    private Long inviterId;
    private String status;

    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public Long getTenantId() {
        return tenantId;
    }

    public void setTenantId(Long tenantId) {
        this.tenantId = tenantId;
    }

    public String getPhone() {
        return phone;
    }

    public void setPhone(String phone) {
        this.phone = phone;
    }

    public Long getInviterId() {
        return inviterId;
    }

    public void setInviterId(Long inviterId) {
        this.inviterId = inviterId;
    }

    public String getStatus() {
        return status;
    }

    public void setStatus(String status) {
        this.status = status;
    }
}

interface UserMapper extends BaseMapper<UserEntity> {
}

interface InviteCodeService {
    InviteCode findByCode(String code);
}

class InviteCode {
    private final String code;
    private final Long ownerUserId;

    InviteCode(String code, Long ownerUserId) {
        this.code = code;
        this.ownerUserId = ownerUserId;
    }

    String getCode() {
        return code;
    }

    Long getOwnerUserId() {
        return ownerUserId;
    }
}

interface MessageClient {
    void sendWelcomeSms(String phone);
}

class BizException extends RuntimeException {
    BizException(String message) {
        super(message);
    }
}

final class TenantContext {
    private static final ThreadLocal<Long> TENANT_ID = new ThreadLocal<>();

    private TenantContext() {
    }

    static void setTenantId(Long tenantId) {
        TENANT_ID.set(tenantId);
    }

    static Long getTenantId() {
        return TENANT_ID.get();
    }

    static void clear() {
        TENANT_ID.remove();
    }
}
```

这段业务代码里有几个测试点：

- 参数校验：手机号为空；
- 上下文校验：租户为空；
- 查询分支：手机号重复；
- 外部依赖：邀请码 service；
- 写库结果：insert 返回 1 或 0；
- 副作用：发送短信；
- 私有配置字段：`defaultStatus`；
- MyBatis-Plus lambda wrapper：`Wrappers.lambdaQuery()`。

### 10.2 完整测试类

```java
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Nested;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;
import org.springframework.test.util.ReflectionTestUtils;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.ArgumentMatchers.anyString;
import static org.mockito.ArgumentMatchers.argThat;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.verifyNoInteractions;
import static org.mockito.Mockito.when;

@ExtendWith(MockitoExtension.class)
@DisplayName("UserServiceImpl 单元测试")
class UserServiceImplTest {

    @Mock
    private UserMapper userMapper;

    @Mock
    private InviteCodeService inviteCodeService;

    @Mock
    private MessageClient messageClient;

    @InjectMocks
    private UserServiceImpl userService;

    @BeforeEach
    void setUp() {
        TenantContext.setTenantId(10L);
        ReflectionTestUtils.setField(userService, "defaultStatus", "NORMAL");
    }

    @AfterEach
    void tearDown() {
        TenantContext.clear();
    }

    @Nested
    @DisplayName("register 方法")
    class RegisterTests {

        @Test
        @DisplayName("租户信息为空时抛异常，并且不访问数据库和远程接口")
        void shouldThrowWhenTenantIsMissing() {
            TenantContext.clear();

            BizException exception = assertThrows(
                    BizException.class,
                    () -> userService.register(new RegisterCommand("13800000000"))
            );

            assertEquals("租户信息不能为空", exception.getMessage());
            verifyNoInteractions(userMapper, inviteCodeService, messageClient);
        }

        @Test
        @DisplayName("手机号为空时抛异常，并且不访问数据库和远程接口")
        void shouldThrowWhenPhoneIsBlank() {
            BizException exception = assertThrows(
                    BizException.class,
                    () -> userService.register(new RegisterCommand(" "))
            );

            assertEquals("手机号不能为空", exception.getMessage());
            verifyNoInteractions(userMapper, inviteCodeService, messageClient);
        }

        @Test
        @DisplayName("手机号已注册时抛异常，并且不插入用户、不发送短信")
        void shouldThrowWhenPhoneAlreadyExists() {
            when(userMapper.selectCount(any())).thenReturn(1L);

            BizException exception = assertThrows(
                    BizException.class,
                    () -> userService.register(new RegisterCommand("13800000000"))
            );

            assertEquals("手机号已注册", exception.getMessage());
            verify(userMapper).selectCount(any());
```

### 10.3 逐行理解这个测试类

先看类头：

```java
@ExtendWith(MockitoExtension.class)
@DisplayName("UserServiceImpl 单元测试")
class UserServiceImplTest {
}
```

含义：

- 启用 Mockito；
- 给测试报告一个中文名称。

这里没有加 `@MockitoSettings(strictness = Strictness.LENIENT)`。新写测试先保持 Mockito 的默认严格检查，能更早发现无效 stub。

再看 mock 和被测对象：

```java
@Mock
private UserMapper userMapper;

@Mock
private InviteCodeService inviteCodeService;

@Mock
private MessageClient messageClient;

@InjectMocks
private UserServiceImpl userService;
```

含义：

- `userMapper` 不查真实数据库；
- `inviteCodeService` 不执行真实邀请码逻辑；
- `messageClient` 不真的发短信；
- `userService` 是真实被测对象，里面会注入这些 mock。

再看准备和清理：

```java
@BeforeEach
void setUp() {
    TenantContext.setTenantId(10L);
    ReflectionTestUtils.setField(userService, "defaultStatus", "NORMAL");
}

@AfterEach
void tearDown() {
    TenantContext.clear();
}
```

含义：

- 每个测试前设置租户 ID；
- 给没有 Spring 容器注入的 private 配置字段赋值；
- 每个测试后清理 ThreadLocal，避免影响下一个测试。

外层的 `@BeforeEach` 和 `@AfterEach` 会作用到内层 `@Nested` 里的每个测试方法。

再看异常分支：

```java
BizException exception = assertThrows(
        BizException.class,
        () -> userService.register(new RegisterCommand(" "))
);

assertEquals("手机号不能为空", exception.getMessage());
verifyNoInteractions(userMapper, inviteCodeService, messageClient);
```

这段测试不是只看“有没有异常”，还看：

- 异常消息是不是对的；
- 参数都不合法时，不能访问数据库；
- 更不能调远程接口。

再看成功分支：

```java
when(userMapper.selectCount(any())).thenReturn(0L);
when(userMapper.insert(any(UserEntity.class))).thenAnswer(invocation -> {
    UserEntity user = invocation.getArgument(0);
    user.setId(1001L);
    return 1;
});

Long userId = userService.register(new RegisterCommand("13800000000"));

assertEquals(1001L, userId);
verify(messageClient).sendWelcomeSms("13800000000");
```

这里我们模拟：

- 查重结果是 0，说明手机号没注册；
- 插入成功，并且模拟数据库回填主键 `1001L`；
- 最后断言返回值是 `1001L`；
- 验证短信接口被调用。

注意，`when(userMapper.selectCount(any())).thenReturn(0L)` 只是用来驱动“手机号未注册”这个业务分支。它没有证明 `LambdaQueryWrapper` 里的租户条件、手机号条件一定写对了。Service 单元测试通常关注业务分支；如果你要验证 SQL 或 wrapper 条件，应该补 Mapper 层测试或 MyBatis-Plus 集成测试。

`thenAnswer` 比 `thenReturn` 更灵活，因为它能拿到传入 mock 方法的参数：

```java
when(userMapper.insert(any(UserEntity.class))).thenAnswer(invocation -> {
    UserEntity user = invocation.getArgument(0);
    user.setId(1001L);
    return 1;
});
```

这很贴近 MyBatis-Plus 的插入行为：真实插入后，主键可能会回填到实体对象里。

### 10.4 如果完整示例遇到 MyBatis-Plus 元信息报错

如果你的 MyBatis-Plus 版本在执行 `Wrappers.<UserEntity>lambdaQuery()` 时提示 TableInfo、lambda cache 或实体元信息未初始化，可以把第 9 节里的初始化方法加到测试类中：

```java
@BeforeEach
void setUp() {
    TenantContext.setTenantId(10L);
    ReflectionTestUtils.setField(userService, "defaultStatus", "NORMAL");
    initMyBatisPlusTableInfo();
}

private void initMyBatisPlusTableInfo() {
    if (TableInfoHelper.getTableInfo(UserEntity.class) != null) {
        return;
    }

    MybatisConfiguration configuration = new MybatisConfiguration();
    MapperBuilderAssistant assistant = new MapperBuilderAssistant(configuration, "");
    TableInfoHelper.initTableInfo(assistant, UserEntity.class);
}
```

对应需要补这些 import：

```java
import com.baomidou.mybatisplus.core.MybatisConfiguration;
import com.baomidou.mybatisplus.core.metadata.TableInfoHelper;
import org.apache.ibatis.builder.MapperBuilderAssistant;
```

这段只在遇到对应问题时加。不要因为项目用了 MyBatis-Plus，就把它复制到所有测试类里。

## 11. 初学者写 Service 单元测试的顺序

不要一打开类就想着“我要把所有行都覆盖”。可以按这个顺序来。

### 第一步：先测最简单的参数校验

例如手机号为空：

```java
@Test
void shouldThrowWhenPhoneIsBlank() {
    BizException exception = assertThrows(
            BizException.class,
            () -> userService.register(new RegisterCommand(" "))
    );

    assertEquals("手机号不能为空", exception.getMessage());
}
```

这种测试不需要太多 mock，最适合上手。

### 第二步：测依赖返回值影响业务分支

例如手机号已存在：

```java
when(userMapper.selectCount(any())).thenReturn(1L);

BizException exception = assertThrows(
        BizException.class,
        () -> userService.register(new RegisterCommand("13800000000"))
);

assertEquals("手机号已注册", exception.getMessage());
```

这里你第一次用到了：

```java
when(...).thenReturn(...)
```

### 第三步：测异常分支有没有提前停止

手机号已存在时不应该插入：

```java
verify(userMapper, never()).insert(any(UserEntity.class));
verify(messageClient, never()).sendWelcomeSms(anyString());
```

这一步开始用：

```java
verify(...)
```

### 第四步：测成功分支

成功分支通常需要准备更多依赖：

```java
when(userMapper.selectCount(any())).thenReturn(0L);
when(userMapper.insert(any(UserEntity.class))).thenReturn(1);

Long userId = userService.register(new RegisterCommand("13800000000"));

verify(userMapper).insert(any(UserEntity.class));
verify(messageClient).sendWelcomeSms("13800000000");
```

### 第五步：再补边界条件

比如：

- mapper 返回 `null` 怎么办？
- insert 返回 0 怎么办？
- 远程接口返回失败怎么办？
- 配置开关关闭时怎么办？
- 租户上下文为空怎么办？

不要一开始就追求“测完所有情况”。先把主流程和关键异常测起来，再逐步补边界。

## 12. 常见误区

### 误区 1：把单元测试写成集成测试

如果你只是想测 `UserServiceImpl.register()` 的业务判断，不要一上来就：

```java
@SpringBootTest
```

`@SpringBootTest` 会启动 Spring 容器，更像集成测试。它有价值，但更慢，也更容易被环境影响。

Service 单元测试优先从这个开始：

```java
@ExtendWith(MockitoExtension.class)
class UserServiceImplTest {
}
```

### 误区 2：只断言返回值，不验证关键副作用

有些方法返回 `void`，或者返回值很简单，但真正重要的是它有没有调用 mapper 或远程接口。

比如：

```java
userService.disableUser(1L);

verify(userMapper).updateById(any(UserEntity.class));
verify(messageClient).sendUserDisabledNotice(1L);
```

这类测试的重点不是返回值，而是交互。

### 误区 3：过度 verify 实现细节

不是所有内部调用都要验证。只验证业务上重要的交互。

比如这些值得验证：

- 不该插入时没有插入；
- 成功后发送了短信；
- 异常时没有发 MQ；
- 调用了远程库存锁定接口。

这些通常不值得验证：

- 某个私有 helper 方法被调用；
- 某个无业务意义的 getter 被调用；
- 内部拆了几个小方法。

测试应该保护业务行为，而不是把实现写死。

### 误区 4：Spy 用 when 导致真实方法提前执行

如果看到这样的 Spy 代码，要警惕：

```java
when(orderService.generateOrderNo()).thenReturn("ORD-001");
```

更稳妥：

```java
doReturn("ORD-001").when(orderService).generateOrderNo();
```

### 误区 5：所有 stub 都写在 @BeforeEach

这样写看起来省事：

```java
@BeforeEach
void setUp() {
    when(userMapper.selectCount(any())).thenReturn(0L);
    when(configService.getSwitch()).thenReturn(true);
    when(remoteClient.querySomething()).thenReturn("OK");
}
```

但后面每个测试都要猜：这些返回值到底哪些被用到了？

更推荐：

```java
@Test
void shouldThrowWhenPhoneAlreadyExists() {
    when(userMapper.selectCount(any())).thenReturn(1L);

    // test body
}
```

把 stub 放在使用它的测试方法附近，读起来最清楚。
