# Spring 事务传播与失效场景

`@Transactional` 可以把一组数据库操作放进事务，但它的边界不是“这个方法里出现的所有代码”。数据库连接、代理调用、线程以及事务管理器，都会影响哪些操作真正参与事务。

本文以 Spring 的命令式事务、JDBC 数据源和默认代理模式为主；响应式事务通过 Reactor 上下文传播，不套用线程绑定的解释。

## 一个事务从哪里开始

在 Spring Boot 已配置数据源、对应事务管理器的前提下，让调用方通过 Spring Bean 调用业务方法：

```java
@Service
public class TransferService {
    private final AccountRepository accounts;

    public TransferService(AccountRepository accounts) {
        this.accounts = accounts;
    }

    @Transactional(rollbackFor = Exception.class)
    public void transfer(long from, long to, BigDecimal amount) {
        accounts.decrease(from, amount);
        accounts.increase(to, amount);
    }
}
```

这里假设两次操作使用同一事务管理器管理的数据源，Repository 使用 Spring 管理的连接。代理在方法执行前开启或加入事务，执行后根据结果决定提交或回滚。

如果方法同时调用远程支付接口，数据库回滚不会撤销那次 HTTP 请求；多个数据源也不会因为加了一个注解就自动具有跨库原子性。

## 七种传播行为

传播行为回答的是：进入方法时，如果已经存在事务，要怎么办？

| 传播行为 | 当前没有事务 | 当前已有事务 |
| --- | --- | --- |
| `REQUIRED`（默认） | 新建事务 | 加入当前事务 |
| `REQUIRES_NEW` | 新建事务 | 挂起当前事务，创建独立事务 |
| `NESTED` | 新建事务 | 在支持的事务管理器下创建保存点 |
| `SUPPORTS` | 非事务执行 | 加入当前事务 |
| `MANDATORY` | 抛异常 | 加入当前事务 |
| `NOT_SUPPORTED` | 非事务执行 | 挂起当前事务，非事务执行 |
| `NEVER` | 非事务执行 | 抛异常 |

`REQUIRED` 的两个方法通常共享同一个物理事务。内层通过代理调用时，如果异常已将共享事务标记为 rollback-only，外层即便捕获异常，提交时仍可能收到 `UnexpectedRollbackException`。

`REQUIRES_NEW` 的提交与外层独立。它适合明确要求独立提交的操作，但外层仍占用原连接，内层往往还要获取新连接；并发量高时需要评估连接池容量，不能随手给每个方法都加上它。

`NESTED` 常见于 JDBC 保存点场景，支持情况取决于事务管理器和驱动。内层可以回滚到保存点，外层继续；外层最终回滚时，内层的修改也会一起回滚。它与独立提交的 `REQUIRES_NEW` 不同，也不能假定所有 JPA 场景都支持。

## 隔离级别：四种标准级别，加一个 DEFAULT

Spring 的 `Isolation` 枚举有五个值，其中 `DEFAULT` 表示采用底层事务系统的默认值，并不是第五种标准隔离级别。

| 枚举值 | 含义 |
| --- | --- |
| `DEFAULT` | 使用数据库/连接的默认隔离级别 |
| `READ_UNCOMMITTED` | 读未提交，可能读到未提交数据 |
| `READ_COMMITTED` | 读已提交，仍可能发生不可重复读 |
| `REPEATABLE_READ` | 可重复读，具体快照与锁行为由数据库实现决定 |
| `SERIALIZABLE` | 串行化隔离，通常需要付出更高并发控制成本 |

MySQL InnoDB 常见默认值是 `REPEATABLE READ`，但连接配置和服务器设置可以改变它，不能只凭数据库名称判断。

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public void updateOrder() {
    // 数据库操作
}
```

显式隔离级别主要在新建事务时生效。如果方法以 `REQUIRED` 加入已有事务，它不会把外层事务切换成另一种隔离级别。常见事务管理器默认允许这种加入；开启 `validateExistingTransaction` 后，可以让不兼容的隔离级别声明尽早报错。

`readOnly = true` 通常是给事务管理器、驱动或 ORM 的优化提示，不能普遍当成“禁止写入”的安全约束。超时和只读配置也需要结合新建还是加入事务、管理器实现判断。

## 异常出现了，为什么没回滚

未额外修改默认规则时，Spring 通常对 `RuntimeException` 和 `Error` 回滚，对受检异常不自动回滚。需要受检异常触发回滚，可以像前面的示例一样明确配置 `rollbackFor`；反过来可用 `noRollbackFor` 指定例外。

Spring Framework 6.2 起还支持通过 `@EnableTransactionManagement(rollbackOn = ALL_EXCEPTIONS)` 统一调整默认规则。排查时应以项目实际版本与配置为准。

```java
@Transactional
public void save() {
    try {
        repository.insert();
        callSomething();
    } catch (Exception e) {
        log.error("保存失败", e);
        // 正常返回：代理不一定知道这里发生过异常
    }
}
```

如果异常在事务方法内部被捕获，代理无法按这个异常决定回滚；但数据库或内层事务也可能已经把事务标记为不可提交。不要用“捕获了异常就一定提交”或“一定回滚”概括所有情况。一般应重新抛出符合回滚规则的异常；业务确需自行处理时，显式设置 rollback-only，并让调用方知道操作未成功。

## 代理没有经过，注解就没有机会生效

常见情况是同一个对象内部自调用：

```java
public void batchSave() {
    this.saveOne(); // 不经过 Spring 代理
}

@Transactional
public void saveOne() {
    repository.insert();
}
```

默认代理模式下，`saveOne()` 的事务声明不会因这次调用而生效。如果外层本身已在事务中，内部数据库操作仍可能参与外层事务，但 `saveOne()` 声明的 `REQUIRES_NEW` 等属性不会被单独应用。

通常把需要独立事务边界的方法拆到另一个 Spring Bean，由外部通过代理调用；手动 `new` 出来的对象、初始化阶段的调用同样不能假定享有代理事务。

方法可见性也要看版本和代理类型：

- 接口代理要求事务方法为接口中声明的 `public` 方法。
- Spring Framework 6.0 起，类代理默认也支持 `protected` 和包可见方法；旧版本或自定义配置可能只处理 `public`。
- `private` 方法不能被覆盖，类代理也无法增强 `final` 方法。

为了让业务边界明确、减少代理差异，事务入口通常仍使用 `public` 方法。有关代理机制可继续阅读 [AOP 知识点](/pages/2be296/)。

## 异步线程与 TransactionTemplate

命令式事务通常绑定到当前线程。`@Async`、线程池或 `CompletableFuture` 启动的新线程，不会自动继承调用线程的事务。

可以在异步任务内部通过另一个受代理 Bean 开启事务，或使用 `TransactionTemplate`：

```java
// transactionTemplate 已由对应的 PlatformTransactionManager 创建
CompletableFuture<Void> task = CompletableFuture.runAsync(() -> {
    transactionTemplate.executeWithoutResult(status -> {
        repository.insertBatch(items);
        repository.recordBatchResult();
    });
}, executor);
task.join();
```

这只保证该回调中、该线程里受同一事务管理器管理的数据库操作形成事务。任务失败会通过 Future 向等待者报告，但其他线程已经提交的事务不会被撤销；主线程之后回滚，也不会回滚这个已提交的事务。

因此，“每个线程各用一个 `TransactionTemplate`”不能实现所有线程一起提交或回滚。若要求批次整体原子性，优先评估单事务批量写入；确需拆分时，需要设计任务状态、幂等与补偿机制。

## 排查顺序与验证

先确认调用是否经过代理，再看事务管理器与数据源是否匹配，然后检查传播行为、异常规则和线程切换。最后检查数据库是否支持事务，以及操作是否真的使用了受管理的连接。

验证时要让事务真正结束后，再从独立连接读取数据。只在带测试事务的测试方法里查询，可能看不到真实提交结果，也容易把测试框架的自动回滚误认为业务事务正确。
