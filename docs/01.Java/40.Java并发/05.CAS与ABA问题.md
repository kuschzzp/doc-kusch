# CAS 与 ABA 问题

多个线程同时执行 `count++`，结果可能少于预期，因为读取、加一、写回是三个步骤。保证这类共享状态更新的正确性，可以先加锁再操作，也可以在更新时检查状态是否仍符合预期。

## 悲观与乐观，是两种协调方式

悲观方式先取得锁，再访问受保护的状态。Java 中常见的工具是 [synchronized](/pages/9f9ed7/) 和 [ReentrantLock](/pages/c77495/)。线程竞争同一把锁时可能等待，但它们能方便地保护一段涉及多个变量的业务逻辑。

乐观方式先基于读到的状态计算，再尝试提交；如果状态已经变化，则重读、重算，或向调用者报告冲突。CAS 和数据库版本号检查都可以用于这种方式，但两者作用的范围不同。

“悲观”和“乐观”不代表一定有冲突或一定没冲突，也不能直接推出谁更快。冲突频率、临界区长度、线程数和等待策略都会影响结果。

## CAS 如何更新一个值

CAS 是 Compare-And-Swap 的简称。可以把 `compareAndSet(expected, update)` 理解成一次原子的“比较并更新”：

- 当前值等于 `expected`：写入 `update`，返回 `true`。
- 当前值不等于 `expected`：不修改，返回 `false`。

比较和更新之间不会被另一个线程插入同一变量的修改。`AtomicInteger` 等原子类提供了这类操作，也提供相应的内存可见性保证；普通 `int` 或单独的 `volatile int` 都不能让 `count++` 变成原子操作。

下面是 Java 8 即可运行的计数示例。保存为 `CasCounterDemo.java`：

```java
import java.util.concurrent.atomic.AtomicInteger;

public class CasCounterDemo {
    private static final AtomicInteger COUNT = new AtomicInteger();

    private static void increment() {
        while (true) {
            int current = COUNT.get();
            if (COUNT.compareAndSet(current, current + 1)) {
                return;
            }
            // 其他线程抢先更新，下一轮重新读取并计算。
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Thread first = new Thread(() -> {
            for (int i = 0; i < 10000; i++) {
                increment();
            }
        });
        Thread second = new Thread(() -> {
            for (int i = 0; i < 10000; i++) {
                increment();
            }
        });
        first.start();
        second.start();
        first.join();
        second.join();
        System.out.println(COUNT.get()); // 20000
    }
}
```

日常计数直接使用 `incrementAndGet()` 即可，手写循环是为了展示失败后如何重试。CAS 循环内的计算可能执行多次，因此不要在其中直接发消息、扣款或执行其他不可重复的外部操作。`updateAndGet` 接收的更新函数也应没有副作用。

## ABA：值相同，不代表期间没有变化

假设线程一读到引用 A，准备稍后更新。线程二先把 A 改为 B，又恢复成原来的 A。线程一执行 CAS 时，比较仍然成功，但它无法得知中间发生过变化。

是否构成问题取决于业务语义。若只关心当前数值，允许其增减后回到原值，ABA 未必有害；若算法依赖“读到之后未发生过修改”，仅比较当前值就不够了，例如复用节点的某些无锁数据结构。

`AtomicStampedReference` 把引用和一个整数版本标记一起比较。这个 stamp 是由程序维护的版本号，**不是系统时间**。每次需要识别的更新都必须推进版本号，才能检测 A → B → A。

下面用顺序操作模拟确定的线程交错，不靠 `sleep` 碰运气。保存为 `AbaDemo.java`：

```java
import java.util.concurrent.atomic.AtomicReference;
import java.util.concurrent.atomic.AtomicStampedReference;

public class AbaDemo {
    public static void main(String[] args) {
        Object a = new Object();
        Object b = new Object();
        Object c = new Object();

        AtomicReference<Object> plain = new AtomicReference<>(a);
        Object oldReference = plain.get(); // 模拟线程一读取。
        plain.compareAndSet(a, b);         // 模拟线程二 A → B。
        plain.compareAndSet(b, a);         // 模拟线程二 B → A。
        System.out.println(plain.compareAndSet(oldReference, c)); // true

        AtomicStampedReference<Object> stamped =
                new AtomicStampedReference<>(a, 0);
        int[] stampHolder = new int[1];
        Object snapshot = stamped.get(stampHolder);
        int oldStamp = stampHolder[0]; // 引用与版本来自同一次读取。

        stamped.compareAndSet(a, b, 0, 1);
        stamped.compareAndSet(b, a, 1, 2);
        System.out.println(stamped.compareAndSet(snapshot, c, oldStamp,
                oldStamp + 1)); // false：引用恢复了，版本已经变为 2。
    }
}
```

使用时还有三个容易忽略的细节：

- 原子引用比较的是对象身份，也就是 `==`，不是 `equals()`；不要依赖装箱整数缓存来演示引用相等。
- 使用 `get(stampHolder)` 一起读取引用和版本，避免分开读取时拼出不属于同一时刻的状态。
- 所有修改路径都要遵守版本协议。反复重用版本、遗漏版本递增或整数最终回绕，都可能使检测失效。

## 适用边界与选择

CAS 适合对单个共享状态做短小更新。竞争较少时，它可以避免线程因互斥锁竞争而挂起；竞争激烈时，反复失败、重算及缓存一致性流量也会消耗资源。无锁算法并不意味着每个线程都能在限定时间内成功，个别线程可能一直重试。

多个原子变量分别更新，不能自动组成一个事务。例如先扣余额再减库存，即使两个字段都是 `AtomicInteger`，仍可能只成功一半。可以用一把锁保护整个不变量，或把有关字段封装为不可变状态，通过一个 `AtomicReference` 整体替换；跨数据库或跨服务的操作还需要相应事务与一致性方案。

对于高竞争的统计计数，可以评估 `LongAdder`，但它的 `sum()` 不是并发更新期间的原子快照，不适合用来判定严格的库存上限。选择原子类或锁时，先明确一致性要求，再结合真实负载测试。
