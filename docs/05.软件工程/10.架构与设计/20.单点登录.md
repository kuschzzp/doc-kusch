# 单点登录

## 一、为什么需要单点登录（SSO）

在互联网时代，企业往往有多个系统：

* OA 办公系统
* 邮件系统
* CRM 客户管理系统
* 财务系统

如果每个系统都要求单独登录，那么用户要：

* 重复输入账号密码；
* 管理多个密码；
* 频繁切换系统时重复认证。

**单点登录（Single Sign-On，简称 SSO）** 就是为了解决这个痛点而生的。
**一句话理解：**

> 用户只需登录一次，即可访问多个相互信任的系统。

---

## 二、SSO 的基本思路

SSO 核心目标是：
让多个系统共享同一个登录态（即「用户已登录」的状态）。

### 举个例子：

你打开公司门户网站 `portal.company.com`，输入账号密码登录。
此时你再访问 `crm.company.com`、`oa.company.com`，系统会自动识别你已登录，不需要再次输入密码。

## 三、SSO 的典型实现流程（原理图）

下面以需要向认证中心验证凭证的方案说明 SSO 流程；具体票据交换方式取决于协议，并非所有实现都逐请求回调认证中心：

```
+--------------------+                 +-------------------+
|  用户（浏览器）     |                 |  SSO 认证中心       |
+--------------------+                 +-------------------+
          |                                          |
          | ① 访问系统 A                              |
          |------------------------------------------>|
          |                                          |
          | ② 系统 A 检测到用户未登录，跳转 SSO 登录页  |
          |<------------------------------------------|
          |                                          |
          | ③ 用户在 SSO 登录页输入账号密码             |
          |------------------------------------------>|
          |                                          |
          | ④ 认证通过，生成登录凭证（如 Token / Ticket） |
          |<------------------------------------------|
          |                                          |
          | ⑤ 浏览器携带 Token 访问系统 A               |
          |------------------------------------------>|
          |                                          |
          | ⑥ 系统 A 向 SSO 验证 Token 有效性           |
          |------------------------------------------>|
          | ⑦ 验证通过，系统 A 创建本地会话              |
          |<------------------------------------------|
          |                                          |
          | 用户已登录系统 A                         |
          |                                          |
```

之后访问系统 B 时（如 `crm.company.com`），流程类似：

1. 系统 B 检测用户未登录；
2. 跳转到 SSO；
3. SSO 发现浏览器已经有登录状态；
4. 自动发放新的 Token 给系统 B；
5. 用户直接登录成功（无需再次输入密码）。

## 四、SSO 的核心组件

| 组件                     | 作用                   |
| ---------------------- | -------------------- |
| **认证中心（SSO Server）**   | 统一的登录服务，负责身份验证和发放令牌  |
| **业务系统（App / Client）** | 需要用户身份信息的各个业务模块      |
| **Token / Ticket**     | 认证中心颁发的登录凭证，用于证明用户身份 |
| **Cookie / Session**   | 浏览器端存储登录状态的机制        |

---

## 五、常见 SSO 实现方式

### Cookie 域共享方案

* 同一个主域名下（如 `*.company.com`）的系统可以共享 Cookie；
* 简单但局限：跨域无法使用。

### Token + SSO Server 方案（推荐）

* 所有系统通过 Token 与 SSO Server 通信；
* 可跨域、跨系统；
* 常用于现代企业级系统（如 CAS、Keycloak、Auth0 等方案）。

---

## 六、SSO 与 OAuth2 的区别

很多新手会混淆这两个概念。它们虽然都与“认证”有关，但出发点不同。

| 对比项            | **SSO（Single Sign-On）** | **OAuth2（Open Authorization）**    |
| :------------- | :---------------------- | :-------------------------------- |
| **目的**         | 用户一次登录访问多个系统            | 授权第三方访问资源（而不暴露密码）                 |
| **场景**         | 多系统共享登录状态               | 微信登录、GitHub 授权登录等                 |
| **核心参与方**      | 用户、SSO 服务端、多个业务系统       | 用户、资源拥有者、授权服务器、第三方应用              |
| **主要流程**       | 登录 → 发 Token → 业务系统验证   | 授权 → 获取 Access Token → 访问资源       |
| **是否跨系统共享登录态** | 是                       | 否（只授权访问资源）                        |
| **典型实现**       | CAS、Keycloak、企业自建认证中心   | 微信 OAuth2、GitHub OAuth2、Google 登录 |

**总结一句话区分：**

> **SSO 解决“登录一次”的问题，OAuth2 解决“授权访问”的问题。**

## 七、OAuth2 也能实现 SSO 吗？

可以，但需要扩展。
很多现代身份框架（如 **OpenID Connect, 简称 OIDC**）是在 OAuth2 之上扩展而来的：

* OAuth2 解决授权；
* OpenID Connect 解决身份认证；
* 两者结合后就能同时实现「登录 + 授权」功能。

采用 OIDC 时，应用请求 `openid` scope，通过 ID Token 获得身份声明，并验证签名、签发者、受众、有效期和需要校验的 `nonce`。Access Token 用于访问受保护资源，不能把任意 Access Token 当成标准的身份凭证。

微信等第三方登录可能使用 OAuth2 授权后调用用户信息接口，是否支持 OIDC 要查对应平台和产品的协议说明，不能一概写成“OAuth2 + OIDC”。

## 八、应用接入、权限缓存与故障边界

### 应用注册不是共享一个密钥

为每个接入应用分配独立 `client_id`，登记精确的回调地址、允许的授权类型和 scope。能够安全保存凭证的后端应用可以使用 `client_secret`，需要做好存储、轮换和吊销；浏览器 SPA、移动端属于公共客户端，不能靠在前端代码中内置 secret 保密。

用户登录通常采用 OIDC 授权码流程并结合 PKCE。认证中心保留自己的登录会话，应用通过授权码交换获得令牌，再建立应用会话；不要把长期令牌直接塞进重定向 URL。服务端会话 Cookie 应设置 `HttpOnly`、`Secure` 及适当的 `SameSite`。

`client_credentials` 表示应用以自身身份调用资源，不代表某个用户登录。Spring Authorization Server 并不原生支持旧式密码授权模式；自建认证中心不等于应让所有应用收集用户密码。

### Redis 缓存能缓解压力，不能消除依赖

| 校验方案 | 认证中心不可用时 | Redis 不可用时 |
| --- | --- | --- |
| 本地验签 JWT | 已有令牌在未过期且所需公钥已缓存时可能继续使用；新登录、刷新以及获取新密钥会受影响 | 若逐请求依赖撤销名单或权限缓存，授权仍会受影响 |
| 不透明 Token + 在线 introspection | 校验请求通常受影响，除非有明确的短期缓存策略 | 取决于认证中心和应用如何存储会话、缓存结果 |
| Redis 共享会话 | 已有会话可能继续使用，但新登录仍依赖认证中心 | 会话读取失败会直接影响登录态判断 |

所以“权限放 Redis，认证中心宕机也不影响业务”不成立。应明确哪些已有会话可以继续使用，以及允许多长的状态滞后；对无法确认权限的敏感操作应拒绝，而不是故障时默认放行。网关验签后，下游还需要受信任的调用链和资源级授权，不能直接信任外部可伪造的用户 Header。

### 权限变更如何生效

角色、菜单和数据权限以业务数据库为准。更新成功后，可以发出权限变更事件，按用户、租户或角色使缓存失效；使用权限版本号帮助识别旧缓存，再配合 TTL 和定期校验处理漏事件。缓存 Key 需要隔离租户与用户。

短有效期能缩小旧权限窗口，但不能保证立即撤权。若 JWT 内嵌权限，修改 Redis 也不会自动改掉已经签发的 JWT；要求及时撤销时，需要在线检查会话/权限版本、撤销名单等机制，同时接受相应的可用性和延迟成本。

菜单用于界面展示，后端仍须针对资源执行授权；隐藏按钮不能替代权限校验。

## 九、总结

| 要点                       | 说明                          |
| ------------------------ | --------------------------- |
| **SSO 是为了解决多系统登录问题**     | 一次登录，多处访问                   |
| **核心机制**                 | 中央认证中心 + Token 验证           |
| **OAuth2 是授权协议，不等于 SSO** | 但可作为 SSO 的基础                |
| **现代实现方式**               | 常用 OpenID Connect 实现统一登录与授权 |
