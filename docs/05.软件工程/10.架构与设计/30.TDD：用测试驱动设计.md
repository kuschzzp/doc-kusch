# TDD：从测试出发思考设计

## 1. 什么是 TDD

TDD（Test-Driven Development，测试驱动开发）是一种围绕测试逐步实现功能的开发方法。开发者先为一个尚未满足的行为写测试，确认它失败，再编写足够的实现让它通过，随后检查代码是否需要重构。

测试先行是这套方法的基本特征。它要求我们在实现之前，先说清楚系统应该在什么条件下做出什么反应。这个反应可以是返回一个结果、拒绝一次操作，也可以是改变状态或发起必要的外部调用。

一次循环通常称为“红—绿—重构”：

- 红：用测试表达预期，确认当前实现还不能满足它。
- 绿：补上当前需要的实现，让新测试和已有测试通过。
- 重构：保持可观察行为不变，整理命名、重复代码、职责和依赖，再运行测试确认。

这几个步骤围绕一个小行为反复进行，不需要一次写完整个功能的所有测试。测试调用的接口尚不存在时，可以先补齐最小接口，再观察它因缺少目标行为而失败。依赖下载失败、测试没有被执行等环境问题，无法提供这类反馈。

TDD 和单元测试也不是同一个概念。单元测试描述测试范围，既可以先写，也可以在实现完成后补写；TDD 描述开发过程，通常借助快速的单元测试推进，也可以结合更外层的验收测试。采用 TDD，并不代表可以省掉集成测试和实际运行环境中的验证。

## 2. 与先实现、后测试的开发方式有什么不同

这里把“传统开发”限定为一种常见流程：分析需求，设计接口和模块，编写实现，再通过测试检查结果。它不等于没有自动化测试，也不意味着必须等全部功能完成后才测试；开发者同样可以小步实现、及时验证。

TDD 调整的是每个小步里的工作顺序：先把预期行为写成测试，再完成对应实现。两种方式都需要理解需求、做设计和检查结果，差异主要在测试何时参与。

| 对比项 | 先实现、后测试 | TDD |
| --- | --- | --- |
| 开始编写一个行为时 | 先决定怎样实现，再检查结果 | 先确定调用条件和预期结果，再写实现 |
| 接口怎样确定 | 主要在设计和实现中形成，随后由测试检验 | 写测试时就要尝试调用接口，使用上的问题更早出现 |
| 遇到模糊规则时 | 可能在需求讨论、实现或测试时发现 | 写预期结果时就必须回答，或者明确留下待确认项 |
| 一步做到哪里 | 按功能或实现任务划分，也可以很小 | 通常推进到当前测试要求的行为 |
| 重构依靠什么 | 依靠已有测试；缺少保护时需要先补充 | 通常已有随开发积累的测试，但保护范围仍需检查 |

例如，一个方法的实现已经写完，补测试时才发现它内部直接创建网络客户端。为了隔离网络，可能需要调整构造方式和调用关系。采用 TDD 时，这个困难更可能在第一批测试中出现，开发者可以趁实现还少，决定把依赖从哪里传入。

这种顺序并不保证设计一定更好。熟悉业务的开发者采用先实现后测试，也能做出清晰的设计；采用 TDD 却只照顾眼前一条断言，也可能写出难以维护的代码。TDD 提供了较早发现问题的机会，能否利用它，仍取决于测试是否表达了有效的业务约定，以及开发者是否愿意据此调整设计。

两种方式也有不同的成本。TDD 把一部分接口思考和测试投入放到了实现之前，起步时可能感觉慢。如果测试执行缓慢、经常无故失败，来回切换只会增加负担。规则尚不明确的探索性工作，可以先做小范围验证，弄清约束后再进入测试先行的循环。

## 3. 为什么测试会影响设计

写测试时，几个设计问题无法绕开：调用者提供什么，能观察到什么结果，需要准备哪些依赖。

如果测试一条业务规则，就得同时准备用户数据库、消息服务和支付网关，可以检查这些准备是否都与当前规则有关。也许这个测试本来就要验证完整流程；也可能是规则判断、数据访问和流程编排混在了一起。后者就值得拆开，让规则能够单独验证，把真实外部系统的协作留给集成测试。

测试还会影响接口的表达方式。调用者应该只需提供完成操作所必需的信息，不必掌握对象内部的每一个步骤。测试若反复需要修改私有状态、调用内部方法才能开始验证，就要检查公开接口是否足以表达这个用例。

这些反馈可以帮助划分职责，但不会自动给出唯一的类结构。把规则放在领域对象、独立策略还是应用服务中，需要结合规则复杂度和已有项目习惯判断。只有一个简单判断时，未必值得增加接口；已经确定有多种变化时，也不必刻意等到代码重复才开始设计。

重构是把这些判断落实到代码的机会。测试通过后，可以调整职责和内部接口，再检查业务结果是否保持不变。测试应保护结果和必要的协作约定，少绑定无关的调用顺序，否则每次重构都要大改测试。

## 4. 测试能够证明到哪里

测试中的期望必须来自业务约定。它无法代替需求确认，也不能因为实现算出了某个结果，就把这个结果反过来当成正确答案。覆盖率只能说明哪些代码执行过，不能证明断言有用。

单元测试能快速检查规则，数据库事务、并发竞争和消息投递则需要相应层次的验证。Mock 返回成功，并不能证明真实系统完成了提交。测试写在实现之前还是之后，都不能改变这个限制。

架构判断同样不能只靠局部测试。服务边界、数据归属、性能目标和故障处理，需要结合实际约束提前考虑。TDD 可以帮助检验其中某个职责或协作接口，无法从一组通过的单元测试中推导出整个系统应该怎样部署。

下面用一个业务场景看看，这些判断怎样落到一次设计过程中。

## 5. 场景推演：用户取消未支付订单

假设我们要给电商系统增加“取消订单”功能。为便于讨论，限定订单和库存由同一个应用管理，存放在同一数据库，可以使用本地事务；订单创建时已经占用库存，本次只处理未支付订单的取消，不涉及退款和跨服务库存同步。以下是示例：

### 先明确“取消成功”指什么

“增加取消按钮”还不足以开始实现。至少需要确认哪些状态能取消、取消后库存怎样处理，以及用户重复点击时会发生什么。

假设业务确认了这些约定：

| 操作前的状态 | 取消请求的结果 | 库存变化 |
| --- | --- | --- |
| 未支付 | 订单变为已取消，返回成功 | 释放该订单占用的库存 |
| 已支付 | 拒绝取消，订单状态不变 | 不释放 |
| 已取消 | 返回已取消的结果，不再次处理 | 不重复释放 |

还要处理订单不存在、非订单所有者发起请求等情况。这里先约定取消入口完成存在性和权限检查，下面只讨论状态变化与库存释放。

这些约定对两种开发方式都适用。使用 TDD 不会凭空得到更多业务知识，它只是要求把约定落实到可执行的预期中。

### 如果先写实现，会怎样展开

一种合理的起点是设计取消接口，在应用服务中读取订单、检查状态、修改状态、释放库存，再补充成功和失败场景的测试。

这种方式可以把功能做好。不过，如果实现时主要沿着“取消成功”这条路径展开，重复请求和支付状态的限制可能到测试阶段才补齐。此时需要回头检查已经安排好的更新顺序和事务范围。

开发者也完全可以在实现前列出这些场景。这里的区别在于，场景是否已经成为能运行的检查，并持续参与每一步修改。

### 第一条测试先确定一次操作的边界

采用 TDD，可以从“未支付订单取消成功”开始：准备一笔占用库存的未支付订单，发起取消，期望订单变为已取消，并释放它占用的库存。

为了写出这个测试，先要决定取消操作从哪里进入。调用者应当提交取消请求，由应用完成状态变化和库存处理。如果接口要求调用者先改订单、再单独调用库存释放，就把一次业务操作拆给了调用者，也更容易漏掉其中一步。

这时可以先确定一个取消用例的入口，以及读取和保存订单、释放库存所需的协作边界。测试中的存储或库存访问可以用替代实现隔离；数据库能否正确提交，稍后单独验证。无需一开始就设计通用订单工作流引擎。

运行测试，确认失败来自取消行为尚未实现，再补上能够通过它的实现。随后检查当前代码是否已经把流程和具体存储方式绑得过紧，有必要就重构。

### 第二条测试让状态规则独立出来

接着加入“已支付订单不能取消”。预期除了返回拒绝，还包括订单状态不变、库存没有释放。只检查一个错误提示，可能漏掉“先释放库存，再发现订单不能取消”的错误。

这条测试要求实现先判断取消是否合法，再产生后续变化。规则究竟放在哪里，也可以在此时讨论。如果订单已经有明确的状态行为，把允许的状态迁移放进订单对象是一个选择；如果项目主要采用简单的应用服务，先把判断保留在那里也可以。

需要关注的是，取消是否合法能否被清楚表达和单独验证，以及其他入口是否会绕过同一条规则。这里并没有一条测试对应一个新类的要求。

### 重复请求会把问题推进到幂等和事务

再加入“已取消订单重复取消”的场景。预期仍然是已取消，但库存不能再次释放。它迫使我们区分两件事：返回成功结果，以及本次是否真的发生了状态变化。

顺序执行的情况下，识别已取消状态就能避免重复处理。并发时却可能有两个请求同时读到未支付状态，因此还需要检查谁有权完成这次迁移。可以考虑用带状态条件的更新等机制，只有成功将订单从未支付改为已取消的请求，才能执行对应的库存释放；未完成迁移的请求再根据订单实际状态决定返回什么。

在这个场景的同库前提下，订单状态变化和库存释放应作为同一个事务提交。释放库存失败时，取消状态也应回滚，避免订单已经取消、库存却仍被占用。

这部分需要数据库集成测试验证，包括重复并发取消是否只释放一次，以及失败时能否整体回滚。支付确认与取消也需要遵守一致的状态迁移约束，不能只在取消一侧做检查。这仍不足以覆盖真实支付渠道已经扣款后的处理，那属于本例未展开的支付协调与补偿问题。

如果第三条测试在已有实现下直接通过，检查它确实验证了不重复释放即可；不必为了展示红灯，故意破坏正确实现。

### 回看这次设计得到了什么

这些场景逐步确定了几个职责：

| 职责 | 本例需要回答的问题 |
| --- | --- |
| 取消用例的应用服务 | 怎样组织读取订单、判断状态和库存处理，并确定事务范围 |
| 订单状态规则 | 什么状态允许取消，重复取消应怎样响应 |
| 持久化与库存访问 | 怎样保证状态迁移和库存变更正确落库，并处理竞争和失败 |

它们未必对应三个类，也不需要拆成三个服务。划分依据是业务规则和协作需要，后续再结合项目规模选择实现形式。

如果以后要支持“已支付但未发货的订单也能取消”，就需要重新确认取消与退款的关系，并更新原来“已支付一律拒绝”的约定。退款是否完成、失败后怎样重试，也会带来新的测试和设计问题。已有测试能保护仍然有效的行为，变化了的规则则应明确替换；本次设计无需提前把整套退款流程建出来。
