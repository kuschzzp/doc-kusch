# 做 Agent 时如何提高 Prompt Cache 命中率：以 OpenAI API 为例

Agent 的请求往往会重复携带系统指令、工具定义、参考资料和历史消息。每次都重新处理这些输入，会增加首 token 延迟和输入费用。

Prompt Caching 复用的是模型处理输入时产生的 KV 状态，不是上一次的回答。后续请求只要在可缓存断点之前拥有相同的渲染前缀，就有机会复用这部分计算。

## 一、Prompt Cache 缓存的不是答案

Prompt Cache 和应用层的 Response Cache 解决的是两件事。

### Prompt Cache

它保存模型已经处理过的输入前缀状态。后续请求命中后，可以跳过这段输入的重复计算，但仍会根据新输入重新生成回答。

```text
固定规则 + 工具定义 + 历史消息 + 新问题
```

两个问题即使很相似，也不会因为命中 Prompt Cache 就直接返回同一份答案。

### Response Cache

Response Cache 是应用自己保存完整响应，例如：

```text
问题 → Redis → 返回已保存的答案
```

它可以绕过模型调用，但要自行处理过期、实时性、权限和隐私。本文只讨论 Prompt Caching。

## 二、OpenAI API 如何匹配缓存

OpenAI 会把请求中的指令、工具、消息以及多模态内容渲染成模型实际看到的上下文。缓存匹配针对的是这段最终上下文的前缀，而不是某一个 API 字段。

可以把 Agent 请求粗略看成：

```text
OpenAI 提供的隐藏内容
工具定义和结构化输出 schema
开发者/系统指令
历史消息、工具调用和工具结果
本轮用户输入
```

上面的顺序只是理解模型输入的示意，并不是固定的序列化格式。工具定义、工具顺序、schema、图片、文件以及消息内容都可能影响渲染后的前缀。

缓存复用要求断点之前的渲染内容完全一致。比如：

```text
请求 1：固定规则 + 固定工具 + 共享资料 + 问题 A
请求 2：固定规则 + 固定工具 + 共享资料 + 问题 B
```

如果共享前缀达到模型要求且缓存仍可用，请求 2 可以复用前面的内容。

相反，把时间戳或请求 ID 放在固定规则前面，会让它们之后的内容都不再是同一个前缀：

```text
system:
你是客服。
当前时间：2026-09-01 10:05:32
请求 ID：abc123
固定客服规则……
```

更稳妥的结构是把动态值放到稳定内容之后：

```text
developer:
你是客服。
固定客服规则……
固定输出格式……

user:
当前时间：2026-09-01 10:05:32
请求 ID：abc123
用户问题：我的订单什么时候发货？
```

如果动态值只是为了日志或排查，可以考虑放进请求 metadata，而不是提示词。

## 三、先用自动缓存，再决定是否加断点

支持的 OpenAI 模型默认启用 Prompt Caching，不需要为了“开启缓存”额外调用接口。先保证以下内容稳定：

```text
稳定的 instructions / developer 消息
稳定的 tools、工具顺序和 schema
不改写的历史消息
动态用户输入放在后面
```

自动缓存并不代表只要文本相同就必然命中。至少要考虑：

- 可缓存前缀要达到模型的最低 token 数；
- 缓存条目会过期，也可能因机器容量被淘汰；
- 请求需要路由到持有匹配条目的机器；
- 模型、区域、工具、schema、图片和相关设置变化，都可能改变前缀；
- 缓存命中率是运行结果，不是固定的 SLA。

当前官方文档给出的最低长度是：GPT-5.6 及以后为 1,024 个可见输入 token；更早的模型通常在 1,024～2,048 之间，具体取决于模型。早期模型的缓存读取还可能按 128 token 粒度报告，因此 `cached_tokens` 不一定等于整段共享内容的长度。

多轮对话尽量追加新消息，不要重写、删除或重新排序旧消息。摘要、截断和 compaction 可以缩短上下文，但也可能让原来的缓存前缀失效，需要权衡输入长度和缓存复用。

## 四、`prompt_cache_key` 是路由提示，不是缓存主键

`prompt_cache_key` 不会把不同的提示词强行视为同一个缓存，也不是权限隔离或加密手段。它会参与请求路由，帮助拥有相同长前缀的请求更可能到达同一缓存位置。

```python
response = client.responses.create(
    model="your-supported-model",
    instructions=STABLE_INSTRUCTIONS,
    tools=STABLE_TOOLS,
    input=[
        *conversation_history,
        {"role": "user", "content": "我的订单什么时候发货？"},
    ],
    prompt_cache_key="support-agent:v3",
)
```

下一次请求应继续使用相同的稳定前缀和 key：

```python
response = client.responses.create(
    model="your-supported-model",
    instructions=STABLE_INSTRUCTIONS,
    tools=STABLE_TOOLS,
    input=[
        *conversation_history,
        {"role": "user", "content": "这个订单可以退货吗？"},
    ],
    prompt_cache_key="support-agent:v3",
)
```

在 GPT-5.6 及以后，如果希望使用官方文档所说的更可靠的断点匹配，应设置稳定的 `prompt_cache_key`；不设置时仍可能得到自动缓存命中，但不会使用这套改进匹配。每个 key 的总流量最好控制在约 15 req/min 以内。更高流量时，可以按租户、会话或稳定哈希分片，但要保证同一类请求持续使用同一分片。

常见设计方式：

```python
# 多个用户共享同一套公共前缀
prompt_cache_key = "support-agent:v3"

# 前缀包含用户独有的长期会话历史
prompt_cache_key = f"support-agent:v3:session:{session_id}"

# 不同租户使用不同的规则
prompt_cache_key = f"support-agent:v3:tenant:{tenant_id}"
```

不要每次生成随机 key：

```python
prompt_cache_key = str(uuid.uuid4())
```

随机 key 会破坏路由分组，通常不利于命中。也不要把密码、API Key 或其他敏感信息直接放入 key。

### Prompt 版本和缓存失效

系统指令、工具描述、参数 schema 或共享资料发生变化时，断点之前的前缀也会变化，旧缓存自然无法匹配。建议把提示词版本写进 key：

```python
prompt_cache_key = "support-agent:v4"
```

升级版本后，新的请求会进入新的路由分组，便于分别观察新旧提示词的命中率和成本，也方便回滚。修改 key 不是“清空缓存”；旧条目仍可能保留到自然过期，且不会被新 key 使用。

如果只是动态用户输入、时间戳或请求 ID 变化，应优先调整它们在请求中的位置，而不是每次都创建新版本。

## 五、什么时候需要显式缓存断点

缓存断点表示“可复用前缀在这里结束”。断点之前的内容必须包含在同一个渲染前缀中，且达到模型的最低可缓存长度。

```text
A：固定规则
B：固定工具
C：共享知识库
D：本次问题

A + B + C | D
          ↑
       缓存断点
```

第一次请求会尝试写入 `A + B + C`，后续请求在这部分完全一致时可以读取它。断点之前任何内容发生变化，都会使该断点对应的前缀无法匹配；断点之后的内容变化不会使这段已缓存前缀失效。

显式断点适合以下情况：

- 固定指令或参考资料较长，已经明显超过最低 token 数；
- 自动断点落在动态内容之后，导致每次都重复写入变化的后缀；
- 不同内容块的更新频率不同，需要分别复用；
- 需要明确控制缓存模式或缓存保留时间。

普通 Agent 可以先依赖隐式缓存，确认 `cached_tokens` 和写入情况后再加断点。

### GPT-5.6 及以后：显式断点示例

Responses API 的顶层 `instructions` 不能直接放 `prompt_cache_breakpoint`。要标记稳定的开发者指令，应把它放在 developer 消息的 `input_text` 内容块上：

```json
{
  "model": "gpt-5.6",
  "prompt_cache_key": "support-agent:v3",
  "prompt_cache_options": {
    "mode": "explicit",
    "ttl": "30m"
  },
  "input": [
    {
      "role": "developer",
      "content": [
        {
          "type": "input_text",
          "text": "固定客服规则和共享知识库……",
          "prompt_cache_breakpoint": {"mode": "explicit"}
        }
      ]
    },
    {
      "role": "user",
      "content": "当前用户的问题……"
    }
  ]
}
```

### Responses API 与 Chat Completions API 的差异

两种 API 都要求断点挂在支持的内容块上，但字段形状不能直接混用：

| API | 可放置断点的内容块（当前文档） | 注意事项 |
|---|---|---|
| Responses API | `input_text`、`input_image`、`input_file` | 顶层 `instructions` 不能直接放断点 |
| Chat Completions API | `text`、`image_url`、`input_audio`、`file`、`refusal` | 需要按 Chat Completions 的消息格式组织内容 |

把断点放在不支持的内容块上，或使用不支持的 `mode`，会返回 `400 invalid_request_error`。如果模型不支持显式断点，应删除这些字段，改用自动缓存。

`mode` 有三种使用思路：

- 默认的 `implicit`：服务会在最新的合适 user 或 tool 消息处设置隐式断点，也会使用显式断点；
- `implicit` + 显式断点：既复用稳定前缀，也允许最新消息形成新的检查点；
- `explicit`：只读取和写入显式标记的断点。若设置了 `explicit` 却没有任何显式断点，该请求不会使用 Prompt Cache，也不会产生缓存写入。

GPT-5.6 及以后每个请求最多写入 4 个新的缓存断点；旧对话中的断点可以被读取，但不会在每次请求中重复写入。使用多个断点前，先确认各段内容确实以不同频率变化，否则只会增加配置复杂度。

`prompt_cache_options.ttl` 当前支持 `30m`。缓存被写入后通常可复用至少 30 分钟，复用会刷新生命周期，但不会再次收取缓存写入费用；实际保留仍可能受模型和系统策略影响。

更早模型使用自动缓存，部分模型支持 `prompt_cache_retention`，可选值和保留时间由模型与组织策略决定，不能把 GPT-5.6 的字段直接套过去。

## 六、如何观测命中和成本

不要只看“请求是否成功”，应记录 usage 中的缓存字段。

对于 Responses API，相关字段在 `usage.input_tokens_details`；对于 Chat Completions API，在 `usage.prompt_tokens_details`。GPT-5.6 及以后通常同时关注 `cached_tokens` 和 `cache_write_tokens`：

```json
{
  "usage": {
    "input_tokens": 3000,
    "input_tokens_details": {
      "cached_tokens": 2000,
      "cache_write_tokens": 500
    }
  }
}
```

这个例子表示：2,000 个 token 从缓存读取，500 个 token 是本次新写入，剩余 500 个按普通输入计费。若 `cache_write_tokens` 长期偏高而 `cached_tokens` 接近 0，优先检查动态时间戳、用户输入、工具结果或不断变化的隐式断点是否位于稳定前缀之前。

在 GPT-5.6 及以后，官方文档给出的计费规则是：缓存读取 token 按未缓存输入价格的 0.1 倍计费，缓存写入 token 按 1.25 倍计费，未读未写的 token 按普通输入价格计费。缓存写入的 1.25 倍是该类 token 的总价，不是在普通输入费用之外再加收一次完整输入费用。更早模型的缓存价格和写入费用可能不同，应以对应模型的价格页为准。

### 缓存率怎么计算和验证

在 GPT-5.6 及以后，可以把 usage 字段聚合成几个工程指标。它们用于比较不同版本和流量配置，不等同于供应商的结算口径：

```text
粗略缓存读取率 = cached_tokens / input_tokens
缓存写入率     = cache_write_tokens / input_tokens
普通输入占比   = (input_tokens - cached_tokens - cache_write_tokens) / input_tokens
```

不要根据一次请求判断命中率，至少分开观察以下场景：

1. 冷启动：第一次请求通常没有缓存读取，可能产生缓存写入。
2. 连续请求：保持断点前缀和 key 不变，检查后续请求的 `cached_tokens`。
3. 前缀变化：修改断点之前的时间戳、工具或 schema，确认命中是否下降。
4. 断点之后变化：只替换用户问题，确认稳定前缀仍能被读取。
5. 低频和高并发：分别观察缓存过期、机器淘汰和单 key 流量过高时的表现。

建议同时记录模型、区域、`prompt_cache_key`、提示词版本、`input_tokens`、`cached_tokens`、`cache_write_tokens`、首 token 延迟（TTFT）和总耗时。只有把这些指标与实际输入价格放在一起，才能判断增加断点或拆分 key 是否真的省钱。

## 七、运行边界

- 缓存读取 token 仍计入 TPM 等速率限制，Prompt Caching 不会提高限流额度。
- 缓存只复用输入处理状态，不会改变输出 token 的生成过程；非确定性请求也不保证每次返回完全相同的内容。
- 缓存不会跨组织共享，也不能跨越区域处理边界复用。`prompt_cache_key` 不是权限控制，应用仍要按租户和会话做好数据隔离。
- 缓存保留时间取决于模型、`ttl`/`prompt_cache_retention` 和组织的数据保留策略；不要把“最多保留多久”当成“必然命中多久”。

## 八、几家 API 厂商的缓存机制速览

不同厂商的字段和 TTL 不是通用标准，下面只列常见接口名；用于生产前请按链接核对当前模型和 SDK 版本。

| 厂商 | 常见机制 | 常见控制方式 | 常见观测字段 |
|---|---|---|---|
| OpenAI | 自动缓存；GPT-5.6 及以后支持显式断点 | `prompt_cache_key`、`prompt_cache_options`、`prompt_cache_breakpoint` | `cached_tokens`、`cache_write_tokens` |
| Claude | 自动缓存和内容块级显式缓存 | `cache_control` | `cache_read_input_tokens`、`cache_creation_input_tokens` |
| DeepSeek | 上下文缓存，按请求前缀复用 | 通常无需额外字段 | `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens` |
| 通义千问 | 隐式缓存和显式缓存 | 以当前 API 的 `cache_control` 等字段为准 | 以当前 API 返回的 `cached_tokens` 等字段为准 |
| GLM | 上下文缓存 | 通常无需手动配置 | 以当前 API 返回的 usage 字段为准 |
