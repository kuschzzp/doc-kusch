# Codex Worktree：紧急需求来了，不必再 stash 和切分支

很多开发者都有过这样的经历。

你正在 `feature/A` 分支开发 A 需求，代码写到一半，还有一些修改没有提交。Codex 也在当前项目中帮你补代码、改测试。就在这时，产品突然通知你：B 需求优先级提高了，今天必须完成。

过去通常只能这样处理：

```bash
# 暂停 A 需求
git stash

# 切换到 B 分支
git switch feature/B

# 完成 B 需求并提交
git add .
git commit -m "feat: complete requirement B"
git push

# 返回 A 分支
git switch feature/A
git stash pop
```

这套流程本身没有问题，但实际操作并不轻松。

`stash pop` 可能产生冲突，IDE 需要重新索引，开发服务需要重新启动，正在执行的 Codex 任务也要停下来。等你处理完 B 再回来，往往还要花时间重新回忆 A 做到了哪里。

Codex Worktree 要解决的，正是这种“一个项目同时有多项工作，但一个工作目录一次只能承载一个现场”的问题。

## Codex Worktree 是什么

Codex Worktree 是 Codex 为单个任务创建的独立代码工作区。

它底层使用的是 Git Worktree，因此并不是一套全新的版本管理机制。Git 负责提供多个工作目录，Codex 在这个基础上负责创建、关联任务、转移代码和清理目录。

### Codex Worktree 和 Git Worktree 有什么不同

两者的文件隔离原理相同：每个 worktree 都有独立的工作目录、`HEAD` 和暂存区，同时共享同一个仓库的提交历史。Codex Worktree 没有替代 Git Worktree，而是在它的基础上增加了任务管理能力。

| 对比项 | Git Worktree | Codex Worktree |
| --- | --- | --- |
| 底层机制 | Git 原生提供的多工作目录能力 | 基于 Git Worktree 创建独立工作区 |
| 创建方式 | 通过 `git worktree add` 手动指定目录、分支或提交 | 在 Codex 中选择 `Worktree` 和起始分支，由应用创建目录 |
| 初始状态 | 可以检出分支，也可以使用 `detached HEAD` | 托管 worktree 默认使用 `detached HEAD` |
| 任务关系 | 不知道 Codex 对话或任务的存在 | 通常与单个 Codex 任务绑定，支持 `Handoff` |
| 生命周期 | 使用 `list`、`move`、`lock`、`remove`、`prune` 等命令自行管理 | Codex 负责快照、恢复和自动清理，也支持创建永久 worktree |
| 忽略文件 | 不会为新目录额外复制 Git 忽略的文件 | 本地托管 worktree 可以通过 `.worktreeinclude` 复制指定的忽略文件 |

如果只是想同时检出多个分支，Git Worktree 已经足够。Codex Worktree 更适合让多个 Codex 任务并行执行，并把工作区的创建、迁移和清理交给应用管理。需要注意的是，Git 的底层限制依然存在：同一个分支不能同时被多个 worktree 检出。

## 用 A、B 两个需求举例

假设项目中有两个分支：

```text
feature/A
feature/B
```

当前状态如下：

```text
本地项目目录
├── 当前分支：feature/A
├── 存在尚未提交的 A 需求代码
└── Codex 正在处理 A 任务
```

这时 B 需求突然变得紧急。

如果继续使用原来的方式，你需要暂停 Codex，暂存 A 的修改，再切换到 `feature/B`。而使用 Codex Worktree 后，A 的开发现场可以保持不动。

你只需要在 Codex 中新建一个任务：

1. 将执行环境选择为 `Worktree`。
2. 将起始分支选择为 `feature/B`。
3. 输入 B 需求并启动任务。

Codex 会创建一个独立工作区。此时的结构大致如下：

```text
同一个 Git 仓库
├── Local
│   ├── 当前分支：feature/A
│   ├── 保留 A 的未提交修改
│   └── A 任务继续执行
│
└── Codex Worktree
    ├── 基于 feature/B 创建
    ├── 保存 B 需求的修改
    └── B 任务独立执行
```

两个任务共享同一套 Git 提交历史，但操作的是不同目录中的文件。

因此，B 任务修改 `OrderService.java` 时，不会把文件写进 A 当前使用的项目目录。A 中尚未提交的代码也不会混进 B 的改动。

你不需要执行 `git stash`，也不需要在 IDEA 当前窗口切换分支。

## 选择起始分支，不等于占用这个分支

创建 Codex Worktree 时，需要选择一个起始分支。例如选择：

```text
feature/B
```

它的含义是：以 `feature/B` 当前的 HEAD 提交作为新任务的起点。

Codex 托管的 worktree 默认处于 `detached HEAD` 状态，也就是指向某个提交，而不是直接检出并占用 `feature/B`。

```text
feature/B
    │
    └── 某个提交
          │
          └── Codex Worktree（detached HEAD）
                ├── 修改订单接口
                ├── 调整数据库查询
                └── 补充单元测试
```

这样设计有一个直接好处：Codex 可以从同一个分支创建多个独立任务，而不必为每个任务提前创建正式分支。

不过，`detached HEAD` 中的修改最终还是需要落到一个分支上，否则不适合长期保留和协作。

## B 需求完成后怎么办

B 需求完成并通过检查后，可以在 Codex 任务顶部选择：

```text
Create branch here
```

然后创建一个正式分支，例如：

```text
codex/B-urgent
```

接下来，可以在这个 worktree 中完成提交和推送，再通过 PR 合入 `feature/B` 或目标分支：

```text
feature/B
    └── codex/B-urgent
          ├── B 需求代码
          └── B 需求测试
```

整个过程中，本地项目仍然停留在 `feature/A`：

```text
Local
├── 当前分支：feature/A
├── A 的未提交代码仍然存在
└── 不需要执行 stash pop
```

B 处理结束后，只需回到 A 的 Codex 对话继续工作。A 的目录、分支和修改状态都没有被 B 打断。

## Handoff 是做什么的

除了在 Worktree 中创建分支，还可以使用 `Handoff` 在 `Local` 和 `Worktree` 之间移动任务。它移动的不只是聊天记录，还包括任务对应的代码状态，并负责处理必要的 Git 操作。

例如，Codex 已经在 Worktree 中完成 B 的主要代码，但你希望：

- 在自己常用的 IDEA 窗口中检查；
- 使用本地已经运行的数据库；
- 通过现有的调试配置排查问题；
- 在 Local 中继续与 Codex 协作。

这时可以将 B 任务 Handoff 到 Local。

不过，在前面的例子中，Local 正在承载尚未完成的 A 需求。此时不适合急着把 B 移回 Local，否则又要处理 A 和 B 的现场切换。

更合理的做法是让 B 留在 Worktree 中完成，通过新分支和 PR 交付。等 Local 空闲，或者确实需要本地环境验证时，再考虑 Handoff。

## Worktree 隔离了什么

Codex Worktree 主要隔离的是项目文件和 Git 工作区状态。

例如，A 和 B 可以分别拥有自己的：

- 源代码修改；
- Git 暂存区；
- 未提交文件；
- 依赖目录；
- 构建产物；
- 测试结果。

但它不是虚拟机，也不是容器，不会隔离所有系统资源。

假设 A 和 B 都执行：

```bash
npm run dev
```

并且都尝试监听 `3000` 端口，后启动的服务仍然可能报端口占用。

类似问题还包括：

- 两个任务连接同一个本地数据库；
- 两边同时修改共享的外部数据；
- 两个服务使用同一个 Redis；
- 测试依赖相同的 Docker 容器；
- 构建脚本操作项目目录之外的公共文件。

因此，文件隔离并不等于运行环境完全隔离。并行启动多个任务时，仍然要检查端口、数据库和外部服务是否会互相影响。

## 为什么 Worktree 中可能没有 `.env`

Codex Worktree 从 Git 检出代码，所以被 Git 跟踪的文件会正常出现。

但 `.env`、`.env.local` 等文件通常写在 `.gitignore` 中，它们不会自动包含在新的工作区里。这可能导致 Codex 在 Worktree 中运行项目时遇到类似错误：

```text
DATABASE_URL is missing
```

对于 Codex 管理的本地 worktree，可以在仓库根目录创建 `.worktreeinclude`，列出需要复制的忽略文件或 `.gitignore` 风格的匹配规则：

```text
.env
.env.local
config/secrets.json
```

Codex 创建本地托管 worktree 时，只会复制其中匹配且被 Git 忽略的文件。这个机制不适用于远程 worktree，也不适用于通过命令行手动创建的 Git Worktree。

这里要控制范围，不要因为图方便就把所有本地配置都复制过去。Worktree 是本机上的另一个真实目录，配置文件中的数据库地址、访问令牌和环境权限仍然有效。

## Worktree 会一直保留吗

Codex 默认创建的是托管 worktree，通常与某个任务绑定，定位更接近“独立、可恢复的任务工作区”，而不是永久项目目录。

它可能包含自己的：

- 项目文件；
- 依赖；
- 构建缓存；
- 测试产物。

多个 worktree 会明显增加磁盘占用。默认情况下，Codex 保留最近使用的 15 个托管 worktree；你可以在设置中调整数量，也可以关闭自动清理。关联任务被归档，或者托管 worktree 的数量超过设定上限时，Codex 会自动清理相应目录。

清理前，Codex 会为工作状态保存快照。之后重新打开相关任务时，可以根据界面提示恢复。

仍在运行的任务、已固定（Pinned）的任务以及永久 worktree，不会被自动清理。
