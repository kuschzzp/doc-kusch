# 人机协同的三种模式：HITL、HOTL 与 HOOTL

## 1. 人在自动化流程中的什么位置

Agent 能调用工具之后，就需要回答一个具体问题：它准备执行的动作，哪些要等人确认，哪些可以自己完成，执行中出现偏差时又由谁处理？

HITL、HOTL 和 HOOTL 可以用来描述这几种安排。这里的 Loop 指系统观察状态、作出决策、执行动作并接收反馈的运行过程。

| 模式 | 英文全称 | 人在流程中的角色 | 执行是否等待人的决定 |
| --- | --- | --- | --- |
| HITL | Human-in-the-Loop | 参与关键判断、补充信息或审批 | 在指定环节等待人的输入后继续 |
| HOTL | Human-on-the-Loop | 监督运行，必要时暂停、纠正或接管 | 正常执行不逐项等人，偏差发生时可以介入 |
| HOOTL | Human-out-of-the-Loop | 不参与所讨论流程中的即时决策与实时监督 | 在预设权限和约束内自行运行 |

中文常译为“人在回路中”“人在回路上”“人在回路外”。不同资料对术语的使用范围略有差异，HOOTL 也有其他缩写写法。本文采用表中的含义，讨论系统运行时的控制安排。训练数据的人工标注、模型评估也可能被称为 HITL，但属于另一种语境。

分类时还要说清楚观察范围。一个流程可能自动处理材料，却在最后提交前等待审批。材料处理这一步可以无人值守，整个流程仍包含 HITL。仅凭“有自动化”或“有人看结果”，无法判断它采用了哪种模式。

## 2. HITL：关键环节由人参与决定

HITL 把人的决定放进执行条件里。比如 Agent 准备了一组代码修改，开发者审阅后才允许合并；或者它发现需求有歧义，先等待人补充业务规则，再继续实现。

人的参与可以发生在多个位置，不必每一步都审批。设计时需要明确哪一个环节必须等待，以及人需要根据什么材料作出判断。

一个只有“是否继续”按钮的弹窗，往往提供不了足够信息。审批者至少应当知道准备执行什么、作用于哪些对象、会产生什么变化。审阅代码时，可以展示具体差异和检查结果；批准数据操作时，则需要展示目标范围和预期影响。

审批还应对应确定的内容。人批准的是当前这组修改，Agent 随后又调整了文件，就不能直接把原来的批准用于新的版本。系统可以把审批绑定到变更版本或请求参数，并在相关内容变化后重新评估是否需要确认。

HITL 的成本是等待和人的注意力。确认请求太频繁，审批者容易形成习惯性点击；材料太少，又会让判断变成猜测。如果没有人在期限内处理，流程应按事先约定保持等待、取消或升级处理，不能把沉默临时解释为同意。

## 3. HOTL：系统自主运行，人保留干预能力

HOTL 允许系统连续执行，由人监督过程，在需要时接管。例如 Agent 持续运行检查、分析失败并尝试修复，开发者可以看到它的修改范围、工具调用和资源消耗，发现方向不对时暂停任务。

这要求监督者既能发现偏差，也有时间和手段改变后续执行。人不必一直盯着屏幕，但告警必须能及时到达有能力接管的人。

只留下日志，通常只能帮助事后调查。如果异常发生后系统已经完成了不可撤销的操作，人再读到告警，就无法阻止那次后果。同样，一个任务几分钟就结束，告警却要等下一次日常巡检才有人处理，也不能把巡检当成有效的实时监督。

因此，HOTL 需要结合任务速度设计。可以限制每批处理量，在关键阶段留出检查点，并提供能够实际生效的暂停或接管入口。如果后果发生得比人反应更快，就要用执行前审批、自动限额或其他强制约束来控制风险，不能单独依赖人盯着运行。

“暂停”也有边界。它可能只阻止下一次工具调用，正在进行的远程请求仍会完成。系统需要区分已经执行、正在执行和尚未执行的动作，让接管者知道接下来应停止、核实还是补偿。暂停流程不会自动撤销已产生的结果。

## 4. HOOTL：在限定范围内无人值守

HOOTL 的流程在正常运行时，不依赖人的即时判断或实时监督。比如隔离环境里的格式检查、固定规则的数据转换，或者权限明确的内部索引更新，都可以考虑这种安排。

人仍然需要事先决定任务目标、工具权限、资源上限和失败处理方式，也可以在事后审计结果。无人值守描述的是运行方式，不能据此推导出系统没有责任人，或拥有任意行动的权限。

选择 HOOTL 时，要看具体操作的后果。即使不修改源数据，读取到的敏感资料也可能经由模型请求或结果输出流向外部；一个能修改文件的任务，如果严格限定在可恢复的隔离目录内，影响反而更容易控制。是否可自动执行，需要同时考虑数据范围、工具能力和输出去向。

任务超出约束时，可以自动停止并保留现场，也可以转交人处理。如果后续需要人作决定，流程就进入了包含人工参与的分支。不能因为常规路径无人值守，就要求异常也必须由 Agent 独自处理到底。

## 5. 怎样选择和组合

这三种模式没有固定的升级顺序。HOOTL 可以减少等待，也可能把错误连续放大；HITL 增加人工判断，但不保证审批者一定能发现问题；HOTL 的效果则依赖信息是否及时，以及人是否来得及采取行动。

选择时，可以从具体动作逐项检查：

| 需要判断的问题 | 对设计的影响 |
| --- | --- |
| 出错后影响哪些人、数据和系统？ | 划定权限与执行范围，判断是否需要事前审批 |
| 动作能否撤销，撤销需要付出什么代价？ | 决定能否先执行再检查；补偿能力不等于完全可逆 |
| 人能否在后果发生前发现并介入？ | 判断 HOTL 是否具有实际干预价值 |
| 预期结果能否自动验证？ | 决定哪些检查可自动完成，哪些仍需要人的判断 |
| 监督者不在线、拒绝或超时后怎么办？ | 明确等待、停止、取消或升级处理的路径 |

模式通常应落到具体阶段和动作上。读取资料、生成草稿、修改文件、发送消息和发布结果，可以分别采用不同的安排。启动任务时的一次授权，也不自动覆盖后续所有动作。

这些安排需要由执行系统落实。提示词可以说明“发布前等待确认”，真正调用发布工具时，执行层仍应检查是否存在有效授权。模型说自己“已经获得同意”，不能替代权限校验。

这与[Harness Engineering](/pages/7e7656/)讨论的运行环境相接：工具、状态记录、审批入口和停止机制，需要支持我们给人安排的角色。架构图上写了“人工监督”，而系统只提供完成通知，这个角色就没有实际落点。

## 6. 场景推演：让 Agent 更新客服知识库

假设一家电商公司用知识库辅助客服回答售后问题。商品部门定期提交说明文档，由 Agent 提取规则、生成问答，再更新检索索引。

这次提交的材料里，有一份现行政策写着“签收后 7 天内可申请退货”，另一份过期活动说明写着“30 天内可申请退货”。如果 Agent 把两者混在一起，客服就可能引用错误的期限。这里的数字只用于说明场景，不代表实际售后规则。

任务已经足够具体：把新资料整理进知识库，同时避免过期政策进入当前回答。接下来可以比较三种设计。它们是对同一任务的不同安排，不是必须依次经历的三个阶段。

### 方案一：审核通过的内容才能进入知识库

采用 HITL 时，Agent 先生成候选问答，把新旧内容差异、引用段落和文档版本交给业务人员审核。在审核完成前，线上知识库继续使用原来的版本。

面对两份期限不同的材料，审核者需要确认适用商品、活动有效期和政策版本。如果“30 天”只适用于已经结束的活动，就不能把它写成所有订单的通用规则。业务人员修正候选内容后，系统才发布这次批准的版本。

人的决定直接影响了哪些内容能够上线。为此，审核页面必须展示判断所需的原文和版本信息。只展示 Agent 整理后的流畅答案，审核者很容易看不到冲突。

这种方案把等待放在发布之前。业务人员暂时没有处理，更新就留在待审核状态；不能因为每天积压的文档多，就默认把未审核内容放行。

### 方案二：允许分批更新，由值班人员监督

如果业务可以接受短时间内发现错误再纠正，可以考虑 HOTL。Agent 按小批次更新索引，系统保留上一版，并持续展示来源、规则差异和抽样问答。值班人员收到异常通知后，可以暂停后续批次，把检索切回已验证的版本。

假设一批更新让退货回答从“7 天”变成了“30 天”。差异检查触发告警，值班人员查看来源，发现引用了过期活动说明，于是暂停剩余更新、切回旧索引，再处理这份材料。

这里人的作用发生在运行过程中，不需要逐条预先批准问答。系统也必须给人留下实际干预的条件：批次范围可控、告警有人接收、索引可以切换，暂停后还能确认哪些内容已经生效。

但切回旧索引，只能纠正后续检索。错误答案如果已经展示给客服或客户，就不能靠回滚索引收回。这种损失是否可接受，决定了 HOTL 能不能用于该类更新。如果业务要求错误政策不得未经审核就生效，那么政策变更仍应设置 HITL，不能只靠事后告警。

### 方案三：只让满足明确规则的更新无人值守

采用 HOOTL 时，需要先限定哪些资料能够自动进入知识库。比如，系统只接收指定政策库中的已发布版本，要求材料带有适用范围、生效时间和版本号，并检查新旧规则是否冲突。

Agent 可以无人值守地提取内容、生成问答、构建索引。执行层依据既定规则校验，满足条件后发布；发现同一适用范围下同时存在“7 天”和“30 天”，则让本次更新失败并保留旧版本。校验规则不应只是一句“请确保答案准确”。

运行期间没有人负责监视每批更新，也没有人临时判断这次冲突。停止是预先定义的处理结果。之后如果转给业务人员确认，异常处理就进入了 HITL 分支，不能再把整条路径都称为无人参与。

这种方案也有漏检范围。假如来源系统把过期文件错误地标为当前有效版本，格式、版本和一致性检查仍可能全部通过。自动校验能执行已定义的规则，不能凭空判断哪份政策才是业务真正认可的。因此，来源维护和业务规则变更仍然需要明确的责任人。

### 最后怎样选择

对这个知识库，可以按内容的性质组合使用：

| 更新内容 | 可以考虑的安排 | 选择依据 |
| --- | --- | --- |
| 从已确认的数据源同步字段明确的商品规格 | HOOTL | 来源和转换规则明确，不符合规则就停止 |
| 调整知识库的分段与检索索引，不改变政策原文 | HOTL | 可以分批观察回答变化，出现问题时暂停并切回旧版 |
| 修改退货期限、适用商品等业务政策 | HITL | 需要业务人员确认含义和影响，发布前作出决定 |

即使只是重建索引，也可能因为分段不当而漏掉政策的适用条件，因此仍要验证检索结果。这里选择 HOTL，是接受有人及时发现并纠正这类偏差，而不是认定技术性修改没有风险。

这样设计之后，人工精力主要用于政策判断和异常处理，规则清楚的同步工作可以自行完成。以后要把某类更新从人工审核改为自动发布，先检查原来审核者到底在判断什么：如果那项判断还无法被可靠地表达和检查，删除审批步骤就只是把问题留给了上线之后。
